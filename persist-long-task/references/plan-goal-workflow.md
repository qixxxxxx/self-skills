# Plan、Goal 与状态文件配合

## 职责边界

| 组件 | 保存什么 | 不负责什么 |
|---|---|---|
| Goal | 最终目标、生命周期、自动续跑状态、可选预算 | 不保存逐文件实施现场，也不能替代检查点 |
| Plan | 给用户看的高层路线和当前阶段 | 不作为恢复真相源，不承载完整证据 |
| `state.json` | 当前步骤、证据、有界近期历史、失败尝试、文件生命周期、决定、阻塞和唯一下一动作 | 不负责自动唤醒任务，也不保存无限事件全文 |
| `journal.json` | 最新预写恢复快照，在状态缺失或落后时恢复 | 不保存长期历史，不替代现场核对 |

数据流只能是：

```text
Goal 定义终点并续跑
        ↓
state.json 决定当前位置与下一动作
        ↓
Plan 镜像高层进度给用户查看
```

发生冲突时始终以现场证据和 `state.json` 为准，再修正 Plan；不得根据 Plan 回退状态文件。

## 配合 Plan

1. 先初始化 `state.json`，再建立 Plan。
2. Plan 保持 3 至 8 个高层步骤；状态文件可以包含更细的原子步骤。
3. 每完成状态步骤后，若跨越了高层阶段，再更新 Plan；不要为每次微小检查点频繁改 Plan。
4. 上下文恢复后，先运行 `resume`，再根据状态重建 Plan 的 `pending`、`in_progress`、`completed`。
5. Plan 只能有一个 `in_progress`；它应覆盖 `current_step` 所属的高层阶段。
6. 新发现的工作如果必须发生在最终审计前，用 `add-step --before <最终步骤ID> --reason ...` 插入；Plan 随后镜像新顺序，不根据旧 Plan 回退状态。

## 配合 Goal

只有用户明确要求使用 Goal，或上层规则明确授权时才创建 Goal。不要因任务很长自行扩大授权。

Goal 目标应包含：

- 用户的最终验收目标；
- 绝对状态文件路径；
- “每次续跑先执行恢复门禁，只从 `next_action` 继续”的约束；
- 不把预算耗尽当作完成的约束。

示例目标文本：

```text
完成 <最终目标>。权威进度位于 <绝对路径>/state.json；每次自动续跑或上下文恢复先读取并审计该文件与实际 diff，只从唯一 next_action 继续，不重做已有有效证据的步骤。仅在全部验收通过后标记 Goal complete。
```

每次 Goal 续跑的顺序：

1. 读取 Goal 当前状态；
2. 运行状态 `resume`；
3. 阅读最近历史、当前步骤尝试和文件生命周期警告，并核对 Git/产物现场；
4. 执行一个原子工作单元；失败或不确定路线先写 `attempt`；
5. 写入 `checkpoint` 或 `complete`；
6. 同步高层 Plan；
7. 若仍有工作，保持 Goal 活动；若真正受阻，遵守 Goal 的阻塞判定规则；
8. 全部验收后先 `finish`，再完成 Goal。

用户在运行中编辑 Goal 或发送改变目标/约束的指令时，立即用 `revise` 同步 `state.json`，再调整 Plan。若三者短暂不一致，暂停业务修改，先完成同步并记录原因。

Goal 仍可能触发上下文压缩。它提供“继续运行”的生命周期，不提供“记住实施细节”的保证；恢复能力来自持续落盘、固定上限的近期轨迹和强制读取状态。完整旧事件不进入恢复上下文。

## 可选增强

如果运行环境支持压缩前后钩子，可让钩子提醒 Agent 写检查点和运行 `resume`。钩子仅是提醒机制：它可能缺失、失败或拿不到完整现场，因此不能替代每个原子步骤后的主动落盘。

若希望项目内所有任务默认执行恢复门禁，可在用户明确授权后把简短规则加入项目 `AGENTS.md`。不要未经许可改写已有项目指令。

可使用以下规则模板：

```markdown
当 `<任务根目录>/.codex/long-task/state.json` 存在且任务未完成时，每个新回合、自动续跑、上下文压缩或 Agent 交接后的第一项任务，必须先运行持久化工具的 `resume`，再核对实际 diff/产物；只从 `next_action` 继续。完成原子工作单元后立即写检查点。不得覆盖状态、重做已有有效证据的步骤，或仅凭聊天摘要宣布完成。
```
