# 项目流程与 Skill 设计

## 目标

逐层确定项目目标、触发边界、顶层流程、阶段细则、工具权限、评价验收、异常回退和责任边界。把通过事务审计的文件状态作为项目讨论权威来源，使任务在上下文压缩、跨时段继续或写入中断后仍能回到唯一阶段、讨论项和下一动作。

不要一开始输出完整方案或创建目标 Skill。先建立可恢复的项目状态，再按层级逐步收敛。

## 必须读取的资源

- 进入讨论、恢复项目或推进确认点时，读取 `references/discussion-workflow.md`。
- 初始化、恢复、迁移、写入、提交或修复项目状态包前，读取 `references/project-state.md`；不得直接编辑现行状态文件。
- 第一次向用户输出项目讨论内容前读取 `references/user-interaction-templates.md`；完整恢复、阶段切换或上下文压缩后继续时重新核对，并按当前事件选择唯一模板。
- 当前问题涉及算法、评分、权重、概率、阈值、分类、排序、迭代、自动回退，或用户要求“讲得更容易懂”时，读取 `references/human-readable-explanations.md`。
- 当前项目涉及报告、清单、审批单、交付文档或其他固定输出模板时，读取 `references/template-definition-standard.md`，在当前阶段讨论中自动补齐逐章展示目的、展示方式、字段顺序、数据来源、空值规则、Markdown实例和一致性检查。
- 仅当用户明确要求开始制作或更新目标 Skill，且关键门槛已经关闭时，读取 `references/skill-finalization.md`。
- 规划目标 Skill 的文件骨架、模块拆分和引用导航时，读取 `references/skill-structure.md`，默认采用“总览入口＋核心模块＋专题分册＋横向附录”的编号式结构。

## 本 Skill 的七阶段元流程

以下七段只描述如何主持讨论、持久化和落地，不是目标 Skill 的业务流程；目标 Skill 自己的顶层流程必须由用户另行确认并写入项目阶段文件。

1. **项目状态初始化**：确认状态包目录，识别已有项目，创建或恢复持久化状态。
2. **恢复与完整性入口**：核对当前检查点、正式版本、阶段和唯一确认点。
3. **定位讨论层级与确认点**：先目标和边界，再顶层流程，再阶段细则；每轮只处理一个关键决定。
4. **聚焦讨论与软检查点**：区分事实、已确认、AI 建议、待确认、临时假设和暂缓项；在最终回复前保存本轮有效新增内容。
5. **用户确认与硬检查点**：用户确认后立即写入正式规则、决定记录和不可变版本；最后提交进度文件。
6. **门槛验收与阶段推进**：依据可验证门槛更新进度，执行结构与语义一致性检查，不用主观百分比。
7. **全局定稿、Skill 落地与用户验收**：证明目标、流程、验收和回退已经闭环；名称、目录和授权全部确认后再制作，内部验证后等待用户最终验收。

异常处理贯穿全部阶段：发现状态不一致时立即冻结推进，保存异常现场；只有能够证明最后有效检查点且已保存异常内容时才恢复，否则询问用户。

## 强制状态规则

- 对长期或多轮项目，使用 `PROJECT.md`、`PROGRESS.md`、`ACTIVE.md`、`DECISIONS.md`、`ITEMS.md`、`stages/`、`versions/`、`recovery/` 和 `.project-state/` 组成项目状态包。
- 用户已指定目录时使用该目录；未指定但只有一个明确项目目录时，展示拟使用的绝对路径并在首次写入前确认；目录不明确时询问，不自行猜测。
- 已有状态包必须先验证项目身份。身份一致且有效时恢复；异常时进入恢复流程；身份不一致或无法判断时询问。不得覆盖或删除原状态包。
- 每个有效回合先运行状态 `resume`；有活动事务时只从命令返回的工作目录继续。
- 每个产生事实、约束、建议、假设、修正、待确认项或阶段变化的回合，都先通过 `begin --kind soft` 和 `commit` 完成软检查点。
- `ACTIVE.md` 顶部保存当前完整快照，底部追加当前确认点的轮次流水。未确认内容不得混入正式规则。
- `ITEMS.md` 保存全部问题、门槛、假设、暂缓项、阻塞项和依赖；切换确认点前必须迁移所有遗留项。
- 用户明确确认或直接给出无歧义规则后，通过硬事务关闭原问题、更新正式规则、创建版本快照并完整准备下一确认点。
- 只有现行 Markdown、manifest、journal、当前版本绑定和 schema 2 基线以来的全部历史快照同时通过 `audit` 才属于有效提交。
- 历史版本只用于审计、比较和回退；正常恢复直接读取完整现行文件，不通过历史版本链推算当前状态。
- 项目状态只按 `active/blocked → ready-for-build → building → awaiting-acceptance → completed` 前向推进；返回设计或完成后修改使用 `reopen`，不得跳过落地授权、内部验证或用户验收。
- 如果用户明确拒绝创建持久化状态，说明无法保证抗上下文压缩；可以继续轻量讨论，但不得声称状态可完整恢复。

## 讨论纪律

- 先确认项目目标和边界，再讨论流程；先确认顶层流程，再展开阶段细则。
- 用户要求“更上层”“更简短”或“先不要细化”时立即回到对应层级。
- 不把 AI 建议写成用户决定。会改变范围、成本、输出或风险且拿不准时必须询问。
- 存在合理选项时最多给 2～3 个，说明目的、场景、优缺点、建议及理由；本轮只要求确认一个关键决定。
- “只确认一个问题”限制问题数量，不限制解释深度。普通阶段规则默认完整说明背景、实际过程、例子、边界、影响和代价；不能只用几句话概括。
- 面向用户优先使用日常语言。专业词第一次出现时先解释含义；内部术语、编号和公式不能代替实际过程说明。
- 涉及算法或数字规则时，先说明它解决什么问题，再用小数字走完一次计算或判断，解释结果代表什么，最后才给公式、权重或阈值。
- 每个阶段最终明确输入、前置条件、动作、输出、完成条件、评价方式、异常回退和责任边界。
- 从零设计新 Skill 时，目标用户、正反触发、输入输出、工具环境、权限副作用、异常兼容、验证维护和 Skill 包装都必须确认或有证据地标记不适用。
- 阶段输出包含固定报告或文档模板时，把模板展示契约作为阶段契约自动讨论和落档；不得只确认章节名称。只有字段选择会改变范围、评价、责任或成本时才增加用户确认，不因普通展示细节另开独立问题。
- 评分必须来自已定义指标、权重、阈值或通过规则。总分必须能够追溯到具体差距。
- 发现术语冲突、跨阶段断裂、循环依赖或无法验收时，指出冲突并重新打开对应门槛，不静默改写已确认决定。

## 完成条件

讨论阶段至少满足：

- 目标、范围、非目标、输入输出和约束明确。
- 顶层流程及顺序已确认。
- 各阶段契约可以执行和验收。
- 所有固定输出模板均逐章定义展示目的、方式、字段顺序、来源、空值规则、Markdown实例和一致性检查。
- 评价、异常、回退、版本和责任边界已经确定。
- 结构校验与语义一致性检查通过。
- 关键待确认项关闭，非关键事项明确记录。
- 所有必需讨论项在 `ITEMS.md` 中终结，活动问题与阻塞唯一且可解释。

目标 Skill 落地至少满足：

- 触发条件、职责边界和工作流与定稿方案一致。
- 主 `SKILL.md` 简洁，详细规则按需拆入 `references/`，确定性操作才进入 `scripts/`。
- 中大型 Skill 默认按 `references/skill-structure.md` 组织；简单 Skill 可以精简，但不得创建空分册或重复内容。
- 元数据、引用和文件结构通过校验，无占位内容。
- 完成正向、负向触发、边界、层级、异常恢复、压缩恢复、落地和独立前向测试。
- 目标 Skill 通过用户最终验收；`project_status=completed`、`current_question=none`，且 `finish` 已写入与当前 revision 匹配的持久证明。

## 输出

项目讨论的最终回复按 `references/user-interaction-templates.md` 选择唯一事件模板；Skill 使用公告、工具进度和其他操作性 commentary 不属于项目讨论模板。先完成模板要求的事务、恢复和审计，再输出当前结论、状态、实际过程、例子、影响、建议和唯一用户动作。普通规则使用标准深度；目标、范围、架构、跨阶段规则、评价、回退和算法使用深入说明。T-05 必须从本次新增决定逐节恢复刚确认规则的原 L2/L3 内容，再完整解释下一确认点；两块任一缺少必需过程或例子时不得发送成功回复。T-06 在询问下一规则前必须完整解释下一确认点；T-10 只能在名称和目录已确认后使用；T-11 只表示等待用户验收，T-12 才表示项目完成。不得虚构编号、把建议写成决定、用术语代替实际过程，或在一轮要求多个独立决定。
