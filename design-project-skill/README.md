# design-project-skill

`design-project-skill` 是一个用于设计和落地 Codex Skill 的中文协作流程。它不会在需求还模糊时直接生成完整 Skill，而是先通过逐轮讨论明确目标、范围、流程、验收标准和异常处理方式，等关键问题确认后，再在用户授权下创建或更新目标 Skill。

## 主要用途

适合以下场景：

- 从零设计一个新的 Skill。
- 把已有的工作流程整理成可复用 Skill。
- 重构职责混乱、规则分散或难以验收的现有 Skill。
- 需要多轮讨论复杂算法、评分标准、报告模板或阶段流程。
- 希望先把方案讨论清楚，再决定是否制作 Skill。
- 项目时间较长，需要在上下文压缩、会话中断或隔天继续后准确恢复。

它重点解决的问题是：避免一开始就过早实现，避免把 AI 的建议误当成用户决定，也避免长时间讨论后遗漏已经确认的规则。

## 大致工作方式

整个过程可以概括为：

1. **建立项目状态**：为本次设计建立可恢复的状态目录，保存项目目标、进度、当前问题、决定记录和历史版本。
2. **逐层讨论**：先确认目标和边界，再确认顶层流程，最后展开各阶段细则；每轮集中解决一个关键决定。
3. **保存检查点**：普通讨论结果写入软检查点，用户正式确认的规则写入硬检查点和版本快照。
4. **检查设计闭环**：确认输入输出、触发边界、工具权限、评价方式、异常回退和责任边界都能够执行和验收。
5. **授权后落地**：只有用户明确要求开始制作或更新 Skill，且名称、目录和关键规则已经确认后，才进入文件编写阶段。
6. **验证与验收**：检查 Skill 的结构、引用、脚本、模板和触发边界，最后等待用户验收。

状态由 `scripts/project_state.py` 统一管理。它提供初始化、恢复、事务提交、审计、修复和完成验收等命令，正常情况下不应手工修改状态文件。

## 项目状态包含什么

长期设计项目通常会保存以下内容：

- `PROJECT.md`：项目目标、范围和约束。
- `PROGRESS.md`：当前阶段和整体进度。
- `ACTIVE.md`：当前讨论问题及最近轮次记录。
- `DECISIONS.md`：已经正式确认的决定。
- `ITEMS.md`：待确认、暂缓、阻塞和依赖事项总账。
- `stages/`：各阶段的详细设计。
- `versions/`：正式版本快照，用于审计、比较和回退。
- `.project-state/`：事务、哈希和恢复所需的内部状态。

这些文件是讨论过程的权威记录。恢复任务时，Skill 会先审计状态，再从唯一的当前问题继续，而不是仅依赖聊天记录回忆。

## 调用示例

可以直接向 Codex 提出：

```text
使用 $design-project-skill，和我逐步设计一个用于代码发布检查的 Skill。先讨论方案，不要立即创建文件。
```

也可以用于改造已有 Skill：

```text
使用 $design-project-skill，重新梳理现有 xxx Skill 的目标、触发范围、流程和验收标准，确认方案后再修改。
```

开始时最好提供：

- 想解决的问题或现有流程。
- 已知的目标用户和使用场景。
- 现有资料或 Skill 路径。
- 希望保存项目状态的位置；如果未指定，Codex 会先确认目录，不会自行猜测。

## 使用特点

- 以用户确认为准，AI 建议不会自动成为正式规则。
- 一轮只确认一个关键问题，但会把该问题的实际过程、例子、边界和影响解释清楚。
- 对算法、评分、阈值等复杂规则，会优先使用普通语言和小例子说明。
- 设计阶段与制作阶段分离，未获得授权时不会提前创建目标 Skill。
- 状态异常时会暂停推进并进入恢复流程，避免覆盖有效记录。

## 目录说明

- `SKILL.md`：Skill 的核心执行规则。
- `references/`：讨论流程、项目状态、交互模板、结构设计和落地验收等详细规范。
- `scripts/project_state.py`：项目状态和事务管理工具。
- `agents/openai.yaml`：Codex 界面展示和默认调用提示。

README 面向使用者提供概览；实际执行时以 `SKILL.md` 和 `references/` 中的规则为准。
