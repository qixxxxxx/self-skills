## 一、使用原则

- 本文件约束项目讨论的最终回复内容，不约束 Skill 使用公告、工具进度、文件写入提示等操作性 commentary。
- 宿主要求使用结构化提问工具时，把模板中的唯一问题映射到该工具，不重复再问第二遍。
- 先完成对应软事务、硬事务、恢复或 audit，再输出成功状态。
- 每轮最终只要求用户作出一个关键决定；不能把“一个问题”误解为只解释几句话。
- 每轮回复自包含，不要求用户回看旧聊天。
- T-02、T-03 默认 L2；目标、范围、架构、跨阶段规则、评价、回退和算法使用 L3。
- 所有编号、状态和计数从现行 `PROGRESS.md`、`ACTIVE.md` 和 `ITEMS.md` 读取。
- 写入、恢复或 audit 失败时只能使用 T-09。
- 用户拒绝持久化时可以轻量讨论，但不得显示虚构版本、检查点或恢复保证。

## 二、状态行与确认点内容契约

### 持久化状态行

```text
状态：<formal_version>｜<checkpoint>｜<soft_checkpoint>｜<current_stage>｜<done>/<total>｜待确认：<current_question>
```

### 轻量讨论状态行

```text
状态：轻量讨论｜不可保证上下文压缩后完整恢复｜待确认：<当前问题>
```

### 完整确认点区块

T-02、T-03、T-05、T-06 和 T-08 在要求用户确认规则前，必须包含：

1. 当前唯一问题及现在确认的原因。
2. 已确认背景和不能改变的约束。
3. 采用后实际怎么运行。
4. 适用和不适用范围。
5. 正常例子；L3 另含边界和异常例子。
6. 对用户、后续阶段、成本、风险和维护的影响。
7. AI 建议及来自现有目标的理由。
8. 本轮确认什么、明确不确认什么。
9. 一个清楚的用户动作。

涉及算法时，另含所需数据、单位、步骤、小数字演算、结果含义、数据缺失和临界处理；公式放在例子之后。

涉及固定输出模板时，另含逐章展示目的、方式、字段顺序、数据来源、空值规则、Markdown 实例和一致性检查。

### T-05 双完整区块

T-05 同一回复包含两个独立内容契约，不能只满足其中一个：

1. **刚确认规则**：从本次硬提交新增的 `DECISIONS.md` 决定块逐节恢复，不从标题、状态行、门槛摘要或聊天记忆概括。L1 至少展示决定、证据和影响；L2 继续实际展示实际过程和正常例子；L3 继续实际展示边界例子和异常例子。决定涉及算法或固定模板时，相应演算、字段和空值规则也必须保留。
2. **下一确认点**：从提交后的 `ACTIVE.md` 恢复完整确认点区块，并保持该问题的 L2/L3 深度。

“已写入 D-xxx”“状态已保存”“audit 通过”只属于状态证明，不能替代刚确认规则的任何必需内容。输出前逐项检查两个区块；缺少任一必需段落时，停止生成成功回复，重新读取对应决定或 `ACTIVE.md` 后补齐。

## 三、事件路由

| 事件 | 前置动作 | 模板 | 用户响应后的路由 |
|---|---|---|---|
| 状态目录未确认 | 不写入；展示绝对路径 | T-01 | 确认后初始化；修改则重新 T-01 |
| 单一建议规则 | 软事务提交完整说明和总账 | T-02 | 确认→硬事务；修改→T-02；歧义→T-04 |
| 2～3 个实质方案 | 软事务提交比较和总账 | T-03 | 选择→硬事务；加条件→T-04/T-03 |
| 用户回复不构成完整确认 | 软事务保存歧义和条件 | T-04 | 澄清后回 T-02/T-03 或硬事务 |
| 当前规则已确认 | 硬事务关闭旧问题并完整准备新问题 | T-05 | 回答新问题后按 T-02～T-05 路由 |
| 阶段门槛全部关闭 | 硬事务提交阶段结果并完整准备下一阶段问题 | T-06 | 回答新问题后按 T-02～T-05 路由 |
| 只查询状态 | `resume`，无变化不建事务 | T-07 | 继续→当前确认模板；回顾→T-08 |
| 首次恢复或压缩后继续 | `resume`、完整 audit 和语义检查 | T-08 | 确认→硬事务；修改→T-02/T-03；异常→T-09 |
| 写入失败、冲突或阻塞 | 冻结并保存恢复现场 | T-09 | 恢复成功→T-08；需决定→等待用户 |
| 定稿、名称和目录均已确认 | 全局 audit；硬/软事务提交 `ready-for-build` 和授权问题 | T-10 | 授权→硬提交 `building` 并制作；拒绝→保持定稿 |
| 目标 Skill 已实现并验证 | 从 `building` 硬提交 `awaiting-acceptance` 和验收问题 | T-11 | 接受→T-12；修改→reopen 后 T-02/T-03 |
| 用户最终接受交付 | 从 `awaiting-acceptance` 硬提交 `completed`；运行 `finish` | T-12 | 项目完成 |

## 四、T-01 状态包目录确认

```markdown
当前结论：需要先建立持久化状态包，长对话或上下文压缩后才能可靠继续。

状态：未初始化｜待确认状态包目录

拟使用目录：`<绝对路径>`

选择依据：<为什么这是唯一合理位置>

将创建：`PROJECT.md`、`PROGRESS.md`、`ACTIVE.md`、`DECISIONS.md`、`ITEMS.md`、`stages/`、`versions/`、`recovery/` 和内部事务元数据。

不会覆盖或删除已有状态包，也不会自行改用其他目录。

请确认：是否使用 `<绝对路径>`？
```

多个候选目录且没有依据时，只说明冲突并请用户指定。

## 八、T-05 硬检查点完成

T-05 既报告刚确认的规则，也完整展示已经软准备好的下一确认点。先识别本次硬提交新增的唯一决定编号，读取该决定完整正文，再按其原 L1/L2/L3 小节恢复；不得只读决定标题或摘要。随后读取提交后的 `ACTIVE.md` 准备下一确认点。无法识别本次新增决定、决定正文不完整或下一确认点不完整时，不能使用 T-05 成功模板，先按 T-09 处理状态问题。

```markdown

<从本次新增决定的“决定”小节恢复完整规则，不压缩成标签>

### 异常例子（L3 必填）
```

## 十六、输出前后检查

### 输出前

- 事件和模板唯一匹配。
- 所需事务、恢复和 audit 已完成。
- 状态编号来自现行文件。
- 未把 AI 建议写成用户决定。
- 当前规则有足够深度和项目内例子。
- T-05 已从本次新增决定正文逐节展示刚确认规则；L2 具备决定、实际过程、正常例子、证据和影响，L3 另具备边界例子和异常例子。
- T-05 的下一确认点也已从新 `ACTIVE.md` 恢复到原 L2/L3 深度；不能用完整的下一确认点掩盖不完整的刚确认规则。
- 所有遗留项已进入 `ITEMS.md`。
- 回复只要求一个用户动作。
- T-10 的名称和目录已经确认。
- T-11 不宣称项目完成；T-12 具有用户验收和 `finish` 证据。

### 用户回复后

- 明确确认规则：硬事务后 T-05/T-06。
- 否定或修改：软事务后 T-02/T-03。
- 部分确认：软事务后 T-04。
- 状态查询：`resume` 后 T-07。
- 恢复：完整 audit 后 T-08。
- 异常：T-09。
- 落地授权：硬提交授权决定后制作。
- 接受交付：硬提交 completed，运行 `finish`，使用 T-12。
- 要求返工：`reopen` 后回 T-02/T-03。
