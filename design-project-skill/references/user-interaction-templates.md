## 一、使用原则

- 第一次向用户输出项目讨论内容前读取本文件；完整恢复、上下文压缩后继续或切换阶段时重新核对。
- 先完成模板要求的状态写入和校验，再发送用户可见回复。模板不能替代软检查点、硬检查点或恢复流程。
- 每轮回复自包含，不要求用户翻看旧聊天才能理解当前结论和问题。
- 正常回复按“当前结论 → 状态 → 本轮内容 → 建议 → 唯一问题”的顺序。
- 每轮最多要求用户确认一个关键决定。多个独立问题拆到后续回合。
- “只确认一个问题”限制的是问题数量，不是解释深度。不能为了简短把规则压缩成几句概括。
- 内部状态可以使用专业字段；用户可见回复优先使用日常语言。专业词第一次出现时先解释含义，再视需要给出术语。
- T-02、T-03 默认达到 L2 标准深度；目标、范围、跨阶段规则、架构、评价、回退或算法问题使用 L3 深入说明。
- 涉及算法、评分、权重、概率、阈值、分类、排序、迭代或自动回退时，先读取 `human-readable-explanations.md`，先讲例子和结果含义，最后才给公式。
- 涉及报告、清单或固定文档模板时，先读取`template-definition-standard.md`，在本轮规则说明中自动加入“输出模板怎么展示”：逐章说明展示目的、方式、字段顺序、数据来源、空值规则和简短Markdown实例。
- 不适用的可选区块可以省略；模板标记为“必填”的字段不得省略。
- 所有版本、检查点、门槛和确认点编号必须从 `PROGRESS.md` 与 `ACTIVE.md` 读取，不凭记忆生成。
- 写入或校验失败时只能使用 T-09，不得继续使用正常讨论模板。
- 用户明确拒绝持久化状态时，状态行必须显示“轻量讨论｜不可保证恢复”，不得显示虚构的版本或检查点。

## 二、状态行与必填字段

### 持久化项目状态行

```text
状态：<formal_version>｜<checkpoint>｜<soft_checkpoint>｜<current_stage>｜<done>/<total>｜待确认：<current_question>
```

总门槛尚未定义时：

```text
状态：<formal_version>｜<checkpoint>｜<soft_checkpoint>｜<current_stage>｜总门槛待定义｜待确认：<current_question>
```

### 轻量讨论状态行

```text
状态：轻量讨论｜不可保证上下文压缩后完整恢复｜待确认：<当前问题>
```

### T-02、T-03 及其他规则讨论模板必填

1. 当前结论。
2. 状态行。
3. 当前唯一确认点或本轮目的。
4. 采用规则后实际会怎么运行。
5. 至少一个与当前项目一致的具体例子；L3 同时包含正常、边界和异常例子。
6. 主要影响、代价或限制。
7. 用户需要执行的唯一动作。

### 有方案选择时必填

1. 每个方案的适用条件。
2. 每个方案的主要优点和缺点。
3. AI 建议及理由。
4. 明确选择格式，例如“A / B / C”。

### 涉及算法时必填

1. 算法解决的实际问题。
2. 一句普通语言说明。
3. 所需数据、单位和提供者。
4. 按顺序展示的计算或判断步骤。
5. 使用小数字完成一次可复算示例。
6. 结果代表什么，以及如何影响实际决定。
7. 数据缺失、并列、刚好通过和刚好不通过时的处理。
8. 公式、权重或阈值放在例子之后，并解释每个符号。

### 涉及固定输出模板时必填

1. 每个章节的展示目的。
2. 展示方式，例如表格、列表、单段结论或代码块。
3. 必需字段、单位、含义和固定顺序。
4. 字段数据来源。
5. 无数据、不适用、样本不足、失败和无法判定的展示方式。
6. 一段字段与正式定义一致的简短Markdown实例。
7. 章节、字段、表头顺序、占位符和机器结果的一致性检查。

## 三、事件到模板的闭环映射

| 事件 | 输出前置动作 | 使用模板 | 用户响应后的路由 |
|---|---|---|---|
| 新项目目录尚未确认 | 不创建状态包；确认候选绝对路径 | T-01 | 确认后初始化并进入 T-02；拒绝或修改则重新确认路径 |
| 当前确认点只有一个建议规则 | 完成软检查点和最小结构校验 | T-02 | 明确确认进入 T-05；修改或否定则更新软检查点并继续 T-02 |
| 当前确认点存在 2～3 个方案 | 完成软检查点和最小结构校验 | T-03 | 明确选择进入 T-05；补充条件则进入 T-04 或更新 T-03 |
| 用户回复不能构成完整确认 | 保存歧义、附加条件和未决点到软检查点 | T-04 | 用户澄清后回到 T-02、T-03 或进入 T-05 |
| 用户已经明确确认 | 完成硬检查点、版本快照和提交后校验 | T-05 | 对模板末尾的新确认点：明确确认再次进入 T-05/T-06；修改进入 T-02/T-03；歧义进入 T-04 |
| 当前阶段全部门槛关闭 | 完成阶段一致性检查并提交状态 | T-06 | 对下一阶段首个确认点：明确确认进入 T-05；修改进入 T-02/T-03；歧义进入 T-04；全局完成进入 T-10 |
| 用户只询问当前状态 | 执行轻量恢复门；无变化时不新建软检查点 | T-07 | 用户要求继续时回到当前 T-02/T-03；要求回顾时进入 T-08 |
| 首次恢复、压缩后继续或需要历史规则 | 执行完整恢复和结构/语义检查 | T-08 | 一致时按当前确认点进入 T-02/T-03；用户直接确认则进入 T-05；不一致时进入 T-09 |
| 写入失败、状态冲突或阻塞 | 冻结推进并保存异常现场 | T-09 | 可确定恢复则复验后 T-08；需用户决定则等待答案 |
| 全局定稿完成，等待落地授权 | 完成全局一致性检查和授权确认点软检查点 | T-10 | 明确授权后硬提交并进入 Skill 落地；未授权则保持定稿 |
| Skill 已制作并验证通过 | 完成最后硬检查点和落地门槛 | T-11 | 项目完成；保留状态包和限制说明 |

## 四、T-01 状态包目录确认

适用于首次写入前。不要在用户确认目录前创建状态包。

```markdown
当前结论：这个项目需要建立持久化状态包，才能在长对话或上下文压缩后继续恢复。

状态：未初始化｜待确认状态包目录

拟使用目录：`<绝对路径>`

选择这个位置的原因：<唯一项目目录、与项目资料同属一个工作区等>

将创建：

- `PROJECT.md`
- `PROGRESS.md`
- `ACTIVE.md`
- `DECISIONS.md`
- `stages/`
- `versions/`
- `recovery/`

不会执行：覆盖已有状态包、改用其他目录、删除已有文件。

请确认：是否使用 `<绝对路径>` 创建项目状态包？
```

如果存在多个候选目录，只说明冲突并询问用户指定目录，不推荐一个未经依据的路径。

## 五、T-02 单一规则确认

适用于当前问题只有一个推荐规则，不需要方案比较。

```markdown
当前结论：<先用普通语言说明建议，不先堆术语>

状态：<状态行>

## 我们现在要决定什么

<Q 编号及本轮唯一问题>

为什么要现在决定：<如果不决定，后面哪些工作无法继续>

## 已经确定的背景

- 已确认事实：
- 不能改变的约束：
- 相关旧决定：<没有则写“无”>

## 采用后会怎么运行

正式规则：<明确、可执行，但先用普通语言表达>

适用情况：<什么情况下按这条规则处理>

不适用情况：<什么情况下不使用这条规则>

实际过程：

1. <先做什么>
2. <接着做什么>
3. <最后得到什么结果>

## 输出模板怎么展示（涉及固定报告、清单或文档时必填）

- 章节与展示目的：
- 展示方式：
- 必需字段、单位、含义和顺序：
- 数据来源：
- 空值、不适用、样本不足和失败规则：
- 一致性检查：
- 简短Markdown实例：

## 举个例子

假设：<使用当前项目中的真实对象和简单数据>

执行过程：

1. ……
2. ……
3. ……

最终结果：<用户会看到什么，以及为什么得到这个结果>

## 特殊情况

- 数据或资料不完整时：
- 刚好达到条件或刚好不满足时：
- 执行失败或发生冲突时：

## 会带来什么变化

- 用户需要多做或少做什么：
- 后续步骤会受到什么影响：
- 主要好处：
- 需要接受的代价或限制：

## 我的建议

我建议：采用上述规则。

理由：<用项目目标、约束和实际影响解释>

## 本轮确认边界

确认后正式写入：<规则、范围、例子、异常和影响>

本轮暂不确认：<没有则写“无”>

请确认：是否按照上述完整规则执行？
```

L2 可以省略确实不适用的特殊情况，但不得只保留结论、理由和一句例子。L3 必须包含正常、边界和异常情况。用户未明确确认时不得关闭决定；用户提出修改后，将修改写入软检查点并重新给出完整当前规则。

```markdown
| 出错后是否容易恢复 | | | |
| 适合什么情况 | | | |
| 不适合什么情况 | | | |
| 对下一步有什么影响 | | | |
| 输出模板字段与顺序 | | | |
| 空值和失败如何展示 | | | |

## 方案 A：<名称>

- 实际执行过程：
- 正常例子：
- 边界或失败例子：
- 主要代价：
- 涉及固定输出时的模板展示契约：

## 方案 B：<名称>

- 实际执行过程：
- 正常例子：
- 边界或失败例子：
- 主要代价：
- 涉及固定输出时的模板展示契约：

## 方案 C：<名称，可选>

- 实际执行过程：
- 正常例子：
- 边界或失败例子：
- 主要代价：
- 涉及固定输出时的模板展示契约：

我的建议：方案 <A/B/C>。

建议理由：<说明它为什么更符合当前目标和约束>

不推荐其他方案的原因：<说明具体不适合之处，不只说“成本高”>
```

## 七、T-04 部分确认或表述歧义

适用于“基本可以”“可以但……”“先这样”或回复无法判断是否正式确认。

```markdown
当前结论：你的回复包含新的条件，目前还不能作为完整确认提交。

状态：<状态行，硬检查点不变，软检查点已更新>

已经明确的部分：

- <明确内容>

仍有歧义的部分：

- <歧义或冲突>

为什么需要澄清：<不同理解会造成的具体影响>

请确认：<只问一个最小澄清问题>
```

澄清后：能形成唯一规则则进入 T-05；仍有方案分歧则回到 T-03。

## 八、T-05 硬检查点完成

只能在硬检查点、目标版本快照和提交后校验全部成功后使用。

```markdown
当前结论：已确认并完成正式落档：<决定摘要>。

状态：<新 formal_version>｜<新 checkpoint>｜<新 soft_checkpoint>｜<current_stage>｜<done>/<total>｜待确认：<新 current_question>

本轮正式记录：

- 决定编号：<D 编号>
- 正式版本：<version>
- 已提交检查点：<checkpoint>

## 你刚刚确认的完整规则

采用规则：<使用用户确认时看到的普通语言版本，不压缩成一句标签>

适用情况：

不适用情况：

实际执行过程：

1. ……
2. ……
3. ……

正常例子：<保留已确认例子和结果>

边界情况：<刚好通过、刚好不通过、资料缺失等>

异常处理：<失败后怎么处理或退回哪里>

主要代价或限制：

如果涉及算法：<保留输入、单位、示例计算、结果含义、权重、阈值和判定顺序>

## 这次确认改变了什么

- 受影响的后续步骤：
- 更新的项目内容：
- 已完成的事项：<门槛编号及普通语言说明>
- 重新打开的事项：<没有则写“无”>
- 被替代的旧规则：<没有则写“无”>

校验结果：结构检查通过；语义检查通过。

下一确认点：<Q 编号及内容>

为什么下一步讨论它：<与刚确认决定的衔接>

请确认：<下一确认点对应的一个问题>
```

如果本次决定关闭了阶段最后门槛，不在此模板追加普通问题，改用 T-06。T-05 的解释深度不得低于用户确认前的 T-02/T-03；不能只保留决定编号和一句摘要。

## 九、T-06 阶段完成与推进

```markdown
当前结论：阶段 `<阶段名称>` 已满足完成条件，可以进入下一阶段。

状态：<状态行>

本阶段完成证据：

- <门槛编号>：<证据>
- <门槛编号>：<证据>

阶段衔接检查：上一阶段输出可以直接作为下一阶段输入；术语和责任边界一致。

下一阶段：<阶段名称>

下一阶段目标：<一句话>

第一个确认点：<Q 编号及内容>

请确认：<下一阶段第一个问题>
```

如果没有下一阶段且全局门槛已经关闭，改用 T-10。

## 十、T-07 状态查询

适用于用户只问“现在到哪了”“还有什么没完成”。没有状态变化时不创建新软检查点。

```markdown
当前结论：<一句话说明当前进度和是否阻塞>

状态：<状态行>

已完成：

- <最近的重要完成项>

当前进行中：<当前阶段和确认点>

阻塞项：<无，或列出编号与原因>

下一步：<用户继续时将处理的唯一问题>
```

不为了填充回复重复完整项目历史。用户要求回顾依据时执行完整恢复并使用 T-08。

## 十一、T-08 完整恢复

```markdown
当前结论：项目状态已从权威文件恢复，可以从现有确认点继续。

有效版本：<formal_version>
已提交检查点：<checkpoint>
软检查点：<soft_checkpoint>
当前阶段：<current_stage 与状态>
最后确认决定：<D 编号及摘要>
当前确认点：<Q 编号及内容>
阶段/全局门槛：<计数>
阻塞项：<数量及摘要>
结构检查：<通过/失败>
语义检查：<通过/失败>

## 当前项目方向

当前目标：<普通语言说明最终要解决什么问题>

当前顶层流程：<用 3～8 个简短步骤说明>

当前阶段要完成什么：<普通语言说明>

## 已确认且不能擅自改变的内容

- <关键规则及含义>

## 当前正在讨论的完整内容

本轮要决定什么：

采用后会怎么运行：

当前例子：<恢复原来保存的正常/边界/异常例子>

如果涉及算法：<恢复输入、示例计算、结果含义和限制；不只恢复公式或最终分数>

下一步：<唯一动作>

请确认：<恢复后当前确认点对应的问题；如果只是状态查询则可省略>
```

任一检查失败时不得使用“可以继续”，改用 T-09。恢复内容必须来自权威文件，不能因为对话压缩而把原来的 L2/L3 说明降成几句概括。

## 十二、T-09 异常、阻塞与恢复

```markdown
当前结论：检测到状态异常，项目推进已冻结，尚未把不完整状态作为正式结果。

恢复事件：<REC 编号>
异常文件：<明确路径列表>
```

## 十五、输出前后检查

### 输出前

- 已选择与当前事件匹配的唯一模板。
- 模板要求的软检查点、硬检查点、恢复或阶段校验已经完成。
- 状态编号来自现行文件。
- 当前结论没有把 AI 建议写成用户决定。
- 回复只要求一个用户动作。
- 不熟悉项目的人能够说出现在要决定什么、采用后会发生什么。
- 专业词已经解释，未用一串术语代替实际过程。
- L2/L3 至少有一个与当前项目一致的例子；L3 包含正常、边界和异常情况。
- 涉及数字、算法、评分、权重、概率或阈值时，已经展示可复算例子，并解释结果代表什么。
- 用户确认后可以直接写入正式规则，不需要 AI 再猜测关键细节。

### 用户回复后

- 明确确认：进入硬检查点，然后 T-05 或 T-06。
- 否定或修改：更新软检查点，继续 T-02 或 T-03。
- 部分确认或歧义：更新软检查点，使用 T-04。
- 只问状态：轻量恢复门后使用 T-07。
- 要求回顾、跨时段继续或压缩后恢复：完整恢复后使用 T-08。
- 出现写入、结构或语义异常：冻结并使用 T-09。
- 明确授权落地：先硬提交授权决定，再进入 `skill-finalization.md`。
