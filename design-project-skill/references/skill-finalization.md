# 从定稿流程落地为 Skill

## 一、进入条件

只有同时满足以下条件才开始制作：

- 用户明确要求创建或更新目标 Skill。
- 项目目标、顶层流程、阶段契约、评价验收和异常回退已经确认。
- 关键门槛关闭；剩余非关键事项已记录且不会改变主体设计。
- 项目状态包通过结构和语义一致性检查。
- 已确定目标 Skill 名称和创建或更新目录。新名称只使用小写字母、数字和连字符。

任一条件不满足时回到讨论工作流，不自行补全重大决定。用户只授权“按建议落地”时，可以采用已经写入 `ACTIVE.md` 且明确标注为 AI 建议的剩余非关键方案；仍不得越过目录、权限、外部发布或高风险操作等授权边界。

## 二、落地前状态提交

1. 执行完整恢复。
2. 确认当前用户授权、目标 Skill 路径和适用范围。
3. 将“进入 Skill 落地”作为正式决定写入硬检查点。
4. 保存定稿摘要：目标、范围、非目标、七阶段流程、阶段契约、评价、异常、回退、当前版本和保留事项。
5. 结构或语义检查失败时停止，不开始编辑目标 Skill。

请求用户授权时使用 `user-interaction-templates.md` 的 T-10。只有收到明确授权并完成对应硬检查点后，才能开始修改目标 Skill。

## 三、确定 Skill 边界

制作前对照定稿方案明确：

| 定义 | 内容 |
|---|---|
| 触发条件 | 用户在什么场景下应使用此 Skill |
| 核心职责 | Skill 必须完成哪些工作 |
| 非职责 | 哪些工作不得由它完成 |
| 完成标准 | 怎样证明一次调用已经完成 |

Description 必须同时说明“做什么”和“何时使用”，并与正文职责一致。

## 四、规划资源结构

- 先读取 `skill-structure.md`。中大型 Skill 默认采用“`SKILL.md` 总览入口＋编号式核心模块＋字母专题分册＋90 系列横向附录”的扁平结构；简单 Skill 可以精简，但不得制造空分册或重复内容。
- `SKILL.md`：只保留触发、总流程、关键分支和必须始终遵守的规则。
- `references/`：保存详细规范、模板、字段、案例和特定阶段规则。
- `scripts/`：只保存需要确定性、重复执行或容易出错的操作。
- `assets/`：只保存最终输出需要复制或使用的资源。
- `agents/openai.yaml`：维护显示名称、简述和包含 `$skill-name` 的默认提示。

不要在 Skill 包中保留讨论过程记录、README、CHANGELOG、安装说明或无关占位文件。需要保留的设计记录移到 Skill 目录之外的明确归档位置，不删除用户资料。

## 五、创建或更新

如果环境提供 `skill-creator`：

1. 完整读取其 `SKILL.md` 和要求的参考文件。
2. 新建 Skill 时先询问目录，并使用初始化脚本建立骨架。
3. 更新现有 Skill 时保留既有目录和用户文件，检查未提交修改，避免覆盖无关内容。

编写要求：

- Frontmatter 只保留 `name` 和 `description`。
- 正文使用命令式表达，明确顺序、分支、停止条件和应读取的参考文件。
- 将已确认分类、评价、异常、版本和责任规则准确映射到执行工作流。
- 不写入历史争议、废弃方案、TODO 或不存在的工具和目录。
- 详细规则拆入参考文件后，必须在 `SKILL.md` 说明何时读取。
- 确定性脚本必须使用用户指定运行环境，并实际执行测试。

## 六、一致性检查

逐项核对：

- Description 的触发场景与正文职责一致。
- Skill 阶段顺序与定稿流程一致。
- 每个关键阶段具有输入、动作、输出、完成条件和异常处理。
- 用户、AI、脚本和外部系统责任边界没有被改写。
- 评价、阈值和验收规则可追溯到定稿决定。
- 引用文件存在，路径和名称正确。
- 文件骨架符合 `skill-structure.md` 的默认结构，或属于有依据的简单 Skill 精简；不存在空分册、重复总览和深层引用链。
- `agents/openai.yaml` 与 `SKILL.md` 一致。
- `user-interaction-templates.md` 覆盖初始化、普通确认、方案比较、歧义、硬提交、阶段推进、状态、恢复、异常、落地授权和落地完成，并且每个模板都能路由到下一状态动作。
- `SKILL.md` 直接说明何时读取 `human-readable-explanations.md`，算法说明遵循“实际问题 → 所需数据 → 执行步骤 → 小数字演算 → 结果含义 → 边界与限制 → 最后给公式”的顺序。
- T-02、T-03 能说明实际运行方式、项目内例子、影响、代价和确认边界；T-05 保留用户刚确认的完整说明；T-08 能恢复原解释深度、完整规则和例子。
- `ACTIVE.md`、`DECISIONS.md` 和正式版本快照能够保存并恢复用户确认时看到的完整说明，不依赖聊天历史重新推测。
- 没有占位内容、无关过程文件和相互冲突的指令。

## 七、验证与试用

1. 运行 Skill 结构验证工具。
2. 运行新增确定性脚本的自测和典型命令。
3. **正向测试**：典型项目设想应先创建或确认状态包、讨论目标和顶层流程，不直接生成完整 Skill。
4. **边界测试**：资料不足、目录不明确或重大选择未定时应暂停询问，不猜测。
5. **层级测试**：用户要求“更上层”或“先不要细化”时应正确收敛。
6. **落地测试**：用户明确授权后，生成结构、引用和验收完整的 Skill，同时保存最终状态。
7. **模板闭环测试**：逐项检查 T-01 至 T-11 的前置状态、用户动作和后续路由，确认写入失败不会进入成功模板，部分确认不会触发硬检查点。
8. **普通用户可读性测试**：让不了解内部术语的人阅读一次 T-02 或 T-03 输出，确认其能复述当前决定、实际过程、主要影响和自己要回答的问题。
9. **专业术语翻译测试**：抽查“阶段门槛、阈值、权重、回退”等词，确认第一次出现时先有普通语言解释，编号和术语没有代替实际过程。
10. **算法示例测试**：使用至少一个评分、权重或阈值场景，确认示例可按给出的数字复算，并能区分综合结果与最低通过要求。
11. **压缩恢复测试**：只依据状态包执行 T-08，确认恢复后的解释深度不下降，正常/边界/异常例子和算法说明没有丢失。

验证失败时只修改导致失败的最小范围并重新验证。

验收通过至少意味着：用户能够用自己的话说明规则，能根据已给例子预测一个相似情况的结果；算法示例可以复算；用户确认后，AI 不需要再猜测权重、阈值、边界或异常处理等关键细节。

## 八、落地完成提交

目标 Skill 验证通过后：

1. 在项目状态包中记录目标 Skill 路径、包含文件、验证命令和结果。
2. 创建最后硬检查点并关闭 Skill 落地门槛。
3. 使用 `user-interaction-templates.md` 的 T-11 向用户报告创建或更新位置、主要文件、验证结果和仍保留的限制。
4. 不删除项目状态包、历史版本、恢复事件或用户源文件。
