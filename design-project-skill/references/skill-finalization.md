# 从定稿方案落地并验收 Skill

## 目录

1. 进入条件
2. 落地前提交
3. Skill 边界和结构
4. 创建或更新
5. 一致性检查
6. 验证与独立前向测试
7. 交付和用户验收

## 一、进入条件

只有以下条件全部满足才开始修改目标 Skill：

- 用户明确授权创建或更新。
- 项目目标、用户确认的顶层流程、阶段契约、评价、异常和回退已确认。
- `discussion-workflow.md` 的从零设计覆盖门槛均已完成或有证据地标记不适用。
- 关键门槛关闭；非关键保留项不会改变主体设计并已进入 `ITEMS.md`。
- 状态包通过 `audit` 和 AI 语义一致性检查。
- 目标 Skill 名称和创建或更新目录已经分别确认。
- `project_status=building`，且所有有效门槛已经完成。
- T-10 中的落地授权已经通过硬检查点提交。

任一条件不满足时回到讨论流程，不自行补全重大决定。目录、权限、外部发布、生产写入和不可逆操作不能由“按建议落地”隐含授权。

## 二、落地前提交

1. 运行 `resume` 和 `audit`。
2. 核对用户授权、目标 Skill 绝对路径、适用范围和现有工作区改动。
3. 核对最近硬事务确实把用户授权和 `project_status=building` 从 `ready-for-build` 一并提交；若尚未提交，先完成该硬事务并重新 audit，不能先编辑目标 Skill。
4. 保存定稿摘要：目标、范围、非目标、用户确认的目标 Skill 顶层流程、阶段契约、评价、异常、回退、当前版本和保留事项。
5. 发现结构、语义或工作区冲突时停止，不编辑目标 Skill。

## 三、Skill 边界和结构

制作前明确：

| 定义 | 必须回答的问题 |
|---|---|
| 触发条件 | 用户什么表达或场景应触发 |
| 非触发条件 | 哪些相似请求不应触发 |
| 核心职责 | Skill 必须完成什么 |
| 非职责 | 哪些工作必须拒绝、停止或交给其他能力 |
| 输入输出 | 需要什么资料，交付什么结果 |
| 工具和权限 | 依赖什么环境、资料、权限和外部系统 |
| 完成标准 | 如何证明单次调用完成 |

Description 同时说明“做什么”和“何时使用”，正文职责不得扩大触发范围。

规划文件结构时读取 `skill-structure.md`：

- `SKILL.md`：触发边界、总流程、关键分支、必须始终遵守的规则和资源导航。
- `references/`：详细规范、字段、模板、案例和阶段规则。
- `scripts/`：确定性、重复执行或容易出错的操作。
- `assets/`：最终输出需要复制或使用的资源。
- `agents/openai.yaml`：显示名称、25～64 字符简述和包含 `$skill-name` 的默认提示。

不要创建 README、CHANGELOG、安装说明、空分册、无关占位文件或讨论过程副本。

## 四、创建或更新

如果环境提供 `skill-creator`：

1. 完整读取其 `SKILL.md` 和所需 reference。
2. 新建 Skill 使用其初始化脚本，不手工伪造骨架。
3. 更新现有 Skill 时检查 Git 状态和用户文件，避免覆盖无关改动。
4. Frontmatter 只保留 `name` 和 `description`。
5. 正文使用命令式表达，明确顺序、条件、停止、恢复和完成门槛。
6. 所有 reference 由主 `SKILL.md` 直接链接，并说明何时读取。
7. 确定性脚本使用用户指定环境并实际运行测试。

用户在制作期间改变目标、范围或约束时，立即停止编辑，通过 `reopen` 重新打开最小必要门槛；不得在目标 Skill 中静默吸收新需求。

## 五、一致性检查

逐项核对：

- Description、正反触发例子和正文职责一致。
- Skill 阶段顺序与用户确认的目标流程一致，而不是照搬本设计 Skill 的七阶段元流程。
- 每个关键阶段具有输入、动作、输出、完成条件、异常和责任边界。
- 工具、环境、权限、外部副作用和停止条件没有被改写。
- 评价、权重、阈值和验收可追溯到已确认决定。
- 固定输出模板的字段、顺序、单位、空值规则、实例和生成/校验逻辑一致。
- 引用文件存在且没有深层引用链、重复权威定义或空文件。
- `agents/openai.yaml` 与 `SKILL.md` 一致。
- 没有 TODO、占位内容、不存在的工具或未经确认的目录。

## 六、验证与独立前向测试

至少执行：

1. Skill 结构校验。
2. 所有新增确定性脚本自测和典型命令。
3. 正向场景：典型请求能走完核心流程。
4. 负向触发：相似但不适用的请求不会错误触发。
5. 边界场景：资料不足、目录不明确和重大选择未定时会停止询问。
6. 层级场景：用户要求“更上层”或“先不要细化”时不会继续展开。
7. 异常和恢复：写入中断、状态冲突、上下文压缩后能从权威状态继续。
8. 模板场景：固定输出字段、顺序、空值和实例一致。
9. 算法场景：示例可复算，综合结果和最低要求明确区分。
10. 落地场景：未授权不创建，授权后结构和状态同步完成。

复杂 Skill 在条件允许时使用新鲜子 Agent 做独立前向测试：只传 Skill 路径、真实用户请求和必要原始资料，不传审查结论、预期答案或修复提示。测试可能耗时、需要额外授权或影响生产系统时，先取得用户同意。

验证失败时修复导致失败的最小范围并重新运行相关场景；不能用窄测试证明广泛完成。

## 七、交付和用户验收

内部验证通过后：

1. 在状态包记录目标 Skill 路径、文件、命令、结果和已知限制。
2. 只有当前状态为 `building` 时，才通过硬事务设置 `project_status=awaiting-acceptance`，建立唯一验收问题。
3. 使用 T-11 报告交付，但不得宣称项目完成。

用户响应：

- **接受**：仅从 `awaiting-acceptance` 硬提交验收决定，关闭全部必需项目，设置 `project_status=completed`、`current_question=none`，运行 `finish` 并确认持久证明与当前 revision 匹配，然后使用 T-12。
- **要求修改**：使用 `reopen`，重新打开最小必要门槛，保留已有文件和测试证据，回到 T-02/T-03。
- **拒绝交付**：保持状态包和目标 Skill 现场，不删除文件，不标记完成。
