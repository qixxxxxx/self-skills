# 从定稿流程落地为 Skill

## 一、进入条件

只有同时满足以下条件才开始制作：

- 用户明确要求创建或更新 Skill。
- 项目目标、顶层流程、关键细则和验收方式已经确认。
- 关键待确认项已关闭；非关键待办已标记，不会改变 Skill 主体设计。
- 已确定 Skill 名称和创建位置。名称应使用小写字母、数字和连字符。

任一条件不满足时，回到讨论工作流，不自行补全重大决定。

## 二、确定 Skill 边界

制作前先写出四项简短定义，并与定稿方案比对：

| 定义 | 内容 |
|---|---|
| 触发条件 | 用户在什么场景下应使用此 Skill |
| 核心职责 | Skill 必须完成哪些工作 |
| 非职责 | 哪些工作不应由它完成 |
| 完成标准 | 怎样证明一次调用已经完成 |

Description 必须同时说明“做什么”和“何时使用”，不要只写概念性介绍。

## 三、规划资源结构

遵循渐进披露原则：

- `SKILL.md`：只保留触发条件、总工作流、关键决策和必须始终遵守的规则。
- `references/`：放详细规范、模板、字段定义、案例和只在特定阶段读取的内容。
- `scripts/`：仅放需要确定性、可重复执行或经常复用的操作；不要为了目录完整而创建。
- `assets/`：仅放最终输出需要复制或使用的模板、图片等素材。
- `agents/openai.yaml`：维护面向用户的名称、简述和默认调用提示。

不要创建与 Skill 执行无关的 README、CHANGELOG、安装说明或过程记录。

## 四、创建与编写

如果环境提供 `skill-creator`，先完整读取其 `SKILL.md` 和被要求的参考文件，并使用其初始化脚本创建骨架。若项目已有 Skill 模板或规范，优先遵循项目规范。

编写时：

1. Frontmatter 仅保留规范允许的字段，至少包含 `name` 和 `description`。
2. 正文使用命令式表达，明确执行顺序、分支、停止条件和需要读取的参考文件。
3. 把讨论中已确认的分类、评价、异常和版本规则准确映射到工作流。
4. 不把历史讨论、争议过程和废弃方案写入执行指令。
5. 不虚构不存在的工具、目录、协议或数据。
6. 详细内容拆入参考文件后，在 `SKILL.md` 明确何时读取，而不是只列出文件名。

## 五、一致性检查

逐项核对：

- Description 的触发场景与正文职责一致。
- Skill 的阶段顺序与定稿流程一致。
- 每个关键阶段都有输入、动作、输出和完成条件。
- 用户与 AI 的责任边界没有被改写。
- 评分、阈值和验收规则可追溯到定稿文档。
- 引用文件存在，路径和名称正确。
- `agents/openai.yaml` 的显示名称、简述和默认提示与 Skill 一致。
- 没有 TODO、示例占位符或相互冲突的指令。

## 六、验证与试用

先运行 Skill 结构验证工具，再进行真实场景测试：

1. **正向测试**：输入一个典型项目设想，检查是否先讨论目标和顶层流程，而不是直接生成完整 Skill。
2. **边界测试**：输入资料不足或重大选择未定的项目，检查是否会暂停并询问，而不是猜测。
3. **层级测试**：用户要求“更上层”或“先不要细化”时，检查是否正确收敛表达。
4. **落地测试**：用户明确确认流程并要求制作时，检查生成结构、引用和验收是否完整。

如果验证或试用失败，只修改导致失败的最小范围，然后重新验证。交付时说明创建位置、包含的文件、验证结果和仍保留的限制。
