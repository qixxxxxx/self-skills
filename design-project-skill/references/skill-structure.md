## 一、结构名称

将中大型 Skill 默认组织为：

> 以 `SKILL.md` 为总览入口、按职责拆分核心模块、按复杂主题增加专题分册、以高编号文件承载横向约束和验收的扁平化编号式文档结构。

该结构用于提高导航稳定性、渐进加载效率、跨模块一致性和后续维护可预测性。它是后续制作 Skill 的主要骨架，不是要求每个 Skill 创建相同数量的文件。

## 二、默认目录映射

```text
skill-name/
├── SKILL.md
│   └── 相当于 00-总览：触发条件、职责边界、总流程、资源导航和停止条件
├── agents/
│   └── openai.yaml
├── references/
│   ├── 01-<核心模块>.md
│   ├── 02-<核心模块>.md
│   ├── ...
│   ├── 06A-<核心模块专题>.md
│   ├── 08A-<复杂主题分册>.md
│   ├── 08B-<复杂主题分册>.md
│   ├── 90-<跨模块一致性>.md
│   ├── 91-<兼容性或边界>.md
│   ├── 92-<命名或字段规范>.md
│   ├── 94-<装配或操作速查>.md
│   ├── 95-<提交前检查清单>.md
│   ├── 96-<职责或运行矩阵>.md
│   └── 97-<最小完整示例>.md
├── scripts/
│   └── 仅放确定性、重复执行或容易出错的操作
└── assets/
    └── 仅放最终输出需要复制或使用的资源
```

默认不再单独创建重复的 `00-总览.md`，由必需的 `SKILL.md` 承担总览入口职责。如果 `references/` 本身规模很大、确实需要独立路由表，可以增加 `references/00-overview.md`，但只做索引，不复制 `SKILL.md` 的流程正文。

## 三、四层职责

### 1. 总览入口

`SKILL.md` 只保留每次触发都必须知道的内容：

- 触发条件和适用场景。
- 核心职责与非职责。
- 顶层工作流和关键分支。
- 必须始终遵守的规则。
- 应在什么条件下读取哪个 reference 或执行哪个 script。
- 停止、询问、回退和完成条件。

不要把完整字段表、长案例、全部变体和重复说明堆入 `SKILL.md`。

### 2. 核心模块

`01～09` 用于按稳定职责拆分主要规则。一个文件对应一个明确模块或工作阶段，并说明其输入、动作、输出、约束和异常边界。

编号表示稳定导航顺序，不自动代表运行顺序。存在执行顺序时必须在 `SKILL.md` 或对应模块中明确说明。

### 3. 专题分册

使用 `06A`、`08A`、`08B` 等形式承载某个核心模块下的复杂主题、玩法族、提供方差异或高级场景。

只有主题内容足以独立加载且不会成为空壳时才创建分册。专题文件必须由 `SKILL.md` 直接链接，避免多层引用链。

### 4. 横向附录

`90～97` 用于承载跨多个核心模块生效、但不适合塞入单一模块的规则：

| 编号段 | 默认职责 |
|---|---|
| `90` | 跨模块一致性与引用校验 |
| `91` | 兼容性边界、已知限制和停止条件 |
| `92～93` | 命名、字段、标识符和术语规范 |
| `94` | 装配、选择或操作速查 |
| `95` | 提交前或交付前自检清单 |
| `96` | 职责矩阵、运行时保留和裁剪边界 |
| `97` | 最小完整示例或最小可验证样例 |

不必机械占满所有编号；只创建实际需要的文件。

## 四、读取顺序

执行目标 Skill 时按以下顺序渐进加载：

1. 完整读取 `SKILL.md`。
2. 根据当前任务读取直接相关的 `01～09` 核心模块。
3. 仅在命中特定复杂主题时读取对应字母分册。
4. 在校验、交付、兼容判断或生成完整结果前读取相关 `90～97` 附录。

不得机械加载全部 reference，也不得只读取专题文件而跳过其核心模块。

## 五、分级结构与精简规则

文件结构服从 `template-definition-standard.md` 已确认的治理等级。

### 简单 Skill

推荐仅保留：

```text
skill-name/
├── SKILL.md
└── agents/openai.yaml
```

只有一段规则明显过长、存在可复用资产，或某个确定性操作反复出现时，才增加一个短reference、asset或script。不要创建编号分册、横向附录、报告生成器、Hash清单或目录汇总作为装饰。

### 标准 Skill

使用`SKILL.md + 少量按职责拆分的references/scripts/assets`。可以采用语义化文件名，不要求为了编号而编号；存在稳定执行顺序或预计长期扩展时再使用`01～09`。固定报告按完整章节契约落入reference或asset，重复和易错操作才脚本化。

### 复杂多阶段 Skill

优先采用本文件的编号式骨架，并按实际需要增加：

- 阶段核心模块与跨阶段一致性附录。
- `assets/templates/`中的阶段报告模板。
- 确定性生成、校验、封存和复算脚本。
- 目录型知识的JSON事实源、中文介绍索引和生成式汇总。
- 版本、Hash、职责矩阵、提交前清单和最小完整示例。

不是所有复杂 Skill 都需要全部组件；未命中的目录、评分、版本或交付后审计要求不得生成空壳文件。

升级判断以阶段依赖、错误代价、复算和维护需求为准。精简时仍保留“单一入口、按需加载、职责清楚、验收可追溯”，但不能通过删文件掩盖已经命中的安全或一致性要求。

## 六、结构校验

制作或更新 Skill 时检查：

- `SKILL.md` 是否是唯一明确入口，并直接链接所有可能需要读取的 reference。
- 核心模块是否按职责拆分，而不是按篇幅平均切割。
- 专题分册是否有明确触发条件，且没有形成深层引用链。
- 横向规则是否集中在附录，避免散落并产生冲突。
- 同一规则是否只保留一个权威定义位置。
- 是否存在空文件、占位内容、重复总览或无实际用途的编号。
- 简单 Skill 是否被过度拆分；复杂 Skill 是否仍把全部细节堆在 `SKILL.md`。
- 简单 Skill 是否无理由增加机器事实源、Hash、生成式汇总或阶段封存；复杂多阶段 Skill 是否缺少已命中的模板、生成、验证、证据或复算组件。
- 最小示例、检查清单和一致性规则能否共同证明 Skill 可执行、可验收。
