## 一、总体原则

- 文件状态是项目讨论的权威来源。聊天记录和上下文压缩摘要只用于辅助，不用于重建正式决定。
- 先目标和边界，后顶层流程；先确认顶层流程，后展开阶段细则。
- 每轮只推进一个层级或一个关键确认点，不一次抛出长问卷。
- 每轮只处理一个关键问题，但必须把该问题解释到用户能够理解、举例验证并作出决定；不能把聚焦误解成只写几句概括。
- 用户可见内容使用普通语言说明实际过程。涉及算法、评分或数字判断时，先讲例子和结果含义，最后再给公式。
- 用户要求“更上层”“更简短”或“先不要细化”时，立即回到对应层级。
- 用户确认后，先完成硬检查点，再进入下一问题。
- 每轮产生有效新增内容时，先完成软检查点，再发送最终回复。
- 任何阶段出现状态冲突、输入输出断裂或无法验收时，冻结推进并重新打开对应门槛。
- 所有用户可见回复按 `user-interaction-templates.md` 的事件映射选择唯一模板；模板要求的写入和校验未完成时不得输出成功状态。

用户只问状态时使用 T-07；首次恢复、压缩后继续或回顾历史时使用 T-08；任何写入、结构或语义异常使用 T-09。其余模板随阶段输出指定。

## 二、阶段 1：项目状态初始化

### 输入

- 项目名称或初步设想。
- 用户已提供的背景、期望结果、资料和约束。
- 用户指定的状态包目录，或唯一明确的项目工作目录。

### 前置条件

- 用户已经明确指定状态包目录；或者已向用户展示拟使用的绝对路径并取得确认。
- 如果存在多个候选目录、没有明确项目目录或写入会影响其他项目，必须询问。

### 动作

1. 提取项目名称、目标摘要、使用者、输入、输出、范围、非目标和约束，不重复询问已明确内容。
2. 建立稳定项目标识。项目标识只使用小写字母、数字和连字符；无法无歧义生成时询问。
3. 检查目标目录是否已有状态包。
4. 已有状态包时，比对项目标识、标题、目标摘要和最后检查点：
   - 身份一致且校验通过：进入阶段 2 恢复。
   - 身份一致但异常：进入异常恢复。
   - 身份不一致或无法判断：停止并询问，不新建、不覆盖。
5. 新项目按 `project-state.md` 创建核心文件和目录，建立 `CP-0000`、`SC-0000` 和 `v0000` 初始状态。
6. 使用 `scripts/project_state.py validate` 执行初始结构校验。

### 输出

- 唯一项目状态包目录。
- 可识别的项目身份。
- 初始项目卡片。
- 初始检查点、版本、阶段和确认点。
- 首次写入前使用 T-01 请求目录确认；初始化成功后使用 T-02 提出首个项目卡片确认点。

### 完成条件

- 核心文件与目录完整。
- 初始版本快照存在并通过校验。
- `PROGRESS.md` 与 `ACTIVE.md` 指向同一阶段和唯一确认点。
- 不存在身份冲突、覆盖风险或未说明的目录假设。

### 异常与责任边界

- AI 负责展示拟写入路径、检查冲突和创建状态包。
- 用户负责确认存在歧义的目录或项目身份。
- 路径不可写、内容冲突或资料目录缺失时停止，不自行改用其他位置。

## 三、阶段 2：恢复与完整性入口

### 输入

- 已确认的状态包目录。
- 当前用户请求。
- 状态包中的现行文件和必要历史版本。

### 动作

每个有效项目回合先执行轻量恢复门：

1. 读取 `PROGRESS.md`。
2. 读取 `ACTIVE.md` 顶部快照。
3. 核对项目标识、当前检查点、正式版本、软检查点、当前阶段、唯一确认点和下一步。

以下情况执行完整恢复：

- 首次打开、跨时段继续或已知发生上下文压缩。
- 轻量文件不一致，或者无法说明为什么正在讨论当前问题。
- 用户要求回顾、修改或推翻以前的规则。
- 当前问题依赖完整项目方案、阶段细则或决定依据。
- 即将执行硬检查点、阶段切换、全局定稿或 Skill 落地。

完整恢复按需读取 `PROJECT.md`、完整 `ACTIVE.md`、当前阶段文件、直接依赖阶段、相关决定和最近已提交版本。不要机械加载无关历史。

### 输出

- 已验证的当前版本和检查点。
- 当前讨论层级、阶段、唯一确认点、门槛进度和阻塞项。
- 校验通过时使用 T-08；用户只问状态且不需要完整恢复时使用 T-07；发现异常时使用 T-09。

### 完成条件

- 当前状态唯一、可解释且结构校验通过。
- 现行文件之间没有检查点、阶段、确认点或引用冲突。
- AI 能明确说明当前确认点来自哪个阶段门槛。

### 异常与回退

发现不一致时按 `project-state.md` 保存异常现场。只有最后已提交检查点明确、版本完整、异常可证明是部分写入且内容已保存时，才恢复；否则询问用户。

## 四、阶段 3：定位讨论层级与确认点

### 输入

- 已恢复的项目状态。
- 当前阶段未关闭门槛。
- 用户最新要求。

### 动作

1. 优先解决最高层且阻断后续工作的未决项。
2. 目标和边界未确认时，不展开顶层流程。
3. 顶层流程未确认时，不机械填满阶段字段。
4. 顶层流程通常保持 4～8 个阶段；超过时检查是否混入子步骤。
5. 每轮建立一个关键确认点，说明：
   - 要确认什么。
   - 为什么现在确认。
   - 会影响哪些后续内容。
   - 使用场景和具体示例。
6. 当前阶段包含固定报告、清单或文档输出时，读取`template-definition-standard.md`，把逐章模板定义纳入同一阶段确认点；普通展示细节不另开问题，影响范围、评价、责任或成本的字段选择仍需确认。
7. 阶段复杂时先拆为 3～7 个子流程，再逐个讨论。
8. 为当前确认点选择解释深度：状态或简单澄清使用 L1，普通规则使用 L2，目标、范围、跨阶段规则、评价、回退和算法使用 L3。
9. 算法、权重、阈值、概率、分类、排序、迭代或自动回退问题必须读取 `human-readable-explanations.md`。

### 输出

- 当前唯一确认点。
- 它对应的门槛、影响范围和确认后的下一步。
- 供阶段 4 在 T-02 或 T-03 中展示的目的、影响和示例。

### 完成条件

- 当前问题不跨越多个层级。
- 用户只需回答一个关键决定。
- 问题答案足以推进下一步，不要求用户补充已经明确的信息。

### 异常与回退

如果当前问题依赖未确认的上层规则，取消该问题并回到上层门槛。不得通过临时猜测固化方向。

## 五、阶段 4：聚焦讨论与软检查点

### 输入

- 当前唯一确认点。
- 用户本轮输入。
- 已确认事实和相关资料。

### 动作

1. 将内容分类为：已知事实、已确认、AI 建议、待确认、临时假设、暂缓/不适用。
2. 按解释深度准备人类可读内容：已知背景、本轮问题、采用后的实际过程、适用与不适用情况、例子、影响、代价和确认边界。
3. L2 至少提供一个正常例子；L3 同时提供正常、边界和异常例子。
4. 涉及算法时，说明实际问题、所需数据、执行步骤、小数字演算、结果含义、边界、限制，最后再给公式或伪代码。
5. 存在多种合理方案时，最多提出 2～3 个，用“实际怎么做、最大好处、最大麻烦、用户需要多做什么、是否容易修改、出错后如何恢复、适合和不适合什么情况”进行比较。
6. 不把建议写成决定；用户表述有歧义且会影响方向时询问。
7. 更新 `ACTIVE.md` 顶部完整快照，并在当前确认点流水中追加本轮记录；保存面向用户的完整解释和例子，不只保存摘要。
8. 当前确认点涉及固定输出模板时，同时保存每章的展示目的、展示方式、必需字段及顺序、数据来源、空值规则、Markdown实例和一致性检查。
9. 如当前确认点、阶段状态或下一步变化，同步更新 `PROGRESS.md`；保持正式检查点不变，递增软检查点编号。
10. 运行最小结构校验和人类可读检查，确认状态一致，并确认用户能够根据例子理解规则结果。
11. 校验成功后再发送最终回复。

### 触发软检查点的变化

- 新事实、新约束或用户修正。
- 新建议、方案、优缺点、理由或示例。
- 新临时假设或替换条件。
- 新增、关闭或改变待确认项。
- 当前层级、阶段、阻塞状态或下一步变化。

纯状态询问、没有新内容的重复说明或只读校验通过，不需要创建新软检查点。校验发现冲突或缺失时仍需落档。

### 输出

- 已持久化的当前讨论快照和流水。
- 简短状态回执。
- 一个清楚的用户确认问题。
- 单一建议规则使用 T-02；存在方案比较时使用 T-03；用户回复不能构成完整确认时使用 T-04。

### 完成条件

- 本轮有效新增内容已经落档并校验。
- 正式规则未混入未确认建议。
- 用户不需要依赖聊天历史理解当前问题。
- 用户确认后可以直接写入正式规则，不需要 AI 再猜测关键细节。
- 涉及算法时，用户能够根据示例预测另一个相似案例的结果。

### 异常与回退

写入或校验失败时，不得声称已保存，也不得进入下一确认点。说明失败文件和未落档内容，修复并重新读取后再继续。

## 六、阶段 5：用户确认与硬检查点

### 输入

- 用户明确确认，或用户直接给出的无歧义正式规则。
- 当前 `ACTIVE.md` 中完整的确认点记录。

### 动作

1. 判断用户输入是否真正构成确认。模糊认可、部分接受或附带新条件时不得自动关闭决定。
2. 生成递增且唯一的决定编号、正式版本和检查点编号。
3. 准备目标版本快照，内容包括新的 `PROJECT.md`、`DECISIONS.md`、`ACTIVE.md`、`PROGRESS.md` 和受影响阶段文件。
4. 先校验目标版本快照。
5. 更新 `DECISIONS.md`，保存目的、场景、选项、优缺点、用户选择、理由、替代关系、面向用户的完整规则、正常/边界/异常例子；涉及算法时同时保存输入、单位、示例计算、结果含义、权重、阈值和判定顺序。
6. 更新 `PROJECT.md` 和受影响阶段文件，只写入已确认规则。
7. 已确认阶段包含固定输出模板时，将完整模板展示契约同步写入对应阶段文件和决定记录，不得只保存章节目录。
8. 将 `ACTIVE.md` 初始化为下一个确认点；上一确认点需要保留的依据已经进入决定记录和版本快照。
9. 执行结构和语义校验。
10. 最后更新 `PROGRESS.md`，提交新的检查点和版本。
11. 重新读取核心文件并执行提交后校验。

### 输出

- 新的正式决定、版本快照和已提交检查点。
- 更新后的门槛状态。
- 下一个唯一确认点。
- 阶段仍在继续时使用 T-05；关闭阶段最后门槛时使用 T-06。

### 完成条件

- 所有目标文件使用同一项目身份、正式版本和检查点。
- `PROGRESS.md` 已最后提交。
- 结构、引用、门槛计数和语义检查通过。
- 用户确认的内容可以从决定记录追溯到正式规则。

### 异常与回退

任何文件编号不一致都视为部分写入。冻结推进并进入恢复事件，不自行选择较新的文件作为有效状态。

## 七、阶段 6：门槛验收与阶段推进

### 输入

- 当前阶段门槛列表。
- 已确认决定和验收证据。
- 结构及语义校验结果。

### 动作

1. 每个门槛记录编号、所属阶段、完成条件、验收证据、状态、关闭依据、责任边界和重开记录。
2. 只有满足完成条件并具有证据的门槛才能计入完成。
3. 新增范围时增加门槛和总数；删除或不适用必须记录决定和理由。
4. 已完成门槛因冲突重新打开时，立即从完成数中移出。
5. 阶段全部必需门槛关闭后，执行阶段输入输出衔接检查，再进入下一阶段。

固定阶段状态：未开始、讨论中、等待确认、已确认、阻塞、重新打开、已完成。

### 输出

- 当前阶段和全项目的门槛完成计数。
- 阶段通过、继续讨论、阻塞或重新打开的结论。
- 阶段通过并进入下一阶段时使用 T-06；全局门槛关闭时使用 T-10；重新打开或阻塞时使用 T-09。

### 完成条件

- 计数可以从门槛明细机械复算。
- 不使用 AI 主观完成百分比。
- 阶段完成能够由证据证明，不由其他阶段的超额完成抵消。

### 异常与回退

发现证据缺失、术语冲突、输入输出断裂或循环依赖时，重新打开最小必要门槛并返回对应层级。

## 八、阶段 7：全局定稿与 Skill 落地

### 输入

- 已确认项目目标、顶层流程和全部阶段契约。
- 评价验收、异常回退、责任边界和版本规则。
- 全局门槛与一致性检查结果。

### 动作

1. 集中检查上一阶段输出能否成为下一阶段输入。
2. 检查术语、对象、状态、单位和责任边界一致性。
3. 检查每项评价指标具有数据来源、计算方式、基准和判定规则。
4. 检查失败条件具有处理人、动作和回退位置。
5. 检查最终输出能够证明顶层目标完成。
6. 输出定稿摘要、当前有效版本、已关闭和保留的待办。
7. 明确询问用户是否进入目标 Skill 落地。
8. 只有用户明确授权后才读取 `skill-finalization.md` 并制作。

### 输出

- 可验收的项目定稿。
- 完整状态包和最终检查点。
- 用户是否授权 Skill 落地的明确结论。
- 请求落地授权时使用 T-10；目标 Skill 验证完成并提交最终状态后使用 T-11。

### 完成条件

- 关键待确认项关闭。
- 非关键待办不会改变主体设计，并已记录。
- 全局结构与语义检查通过。
- 未授权时保持定稿状态，不提前制作。

## 九、方案比较、评价与状态分类

### 状态分类

| 状态 | 含义 |
|---|---|
| 已知事实 | 来自用户、资料或已验证结果 |
| 已确认 | 用户明确接受，已进入硬检查点 |
| AI 建议 | 尚未获得用户确认的方案 |
| 待确认 | 会影响后续设计，必须取得答案 |
| 临时假设 | 为继续推进而采用，可被后续证据替换 |
| 暂缓/不适用 | 本版本不处理，并保留原因 |

### 评价建立顺序

先定义评价对象，再定义指标和算法，最后确定权重、阈值、评分区间或通过规则：

- 评什么：流程、数据、实现、体验或交付完整性。
- 怎么量：计算方法、数据范围、样本和单位。
- 怎么比：基准、容差、权重和聚合方式。
- 怎么判：通过、需调整和阻断条件。
- 怎么解释：总结果必须追溯到阶段、指标和差距。

向用户解释评价算法时，先用当前项目中的小数字完成一次计算，再说明公式。必须区分“综合得分”和“最低通过要求”，并解释数据缺失、并列、刚好通过和刚好不通过时的处理。

当前只需对齐指标时，不提前加入置信度、稳定性或优先级模型；将它们记录为后续候选。

## 十、跨阶段一致性

集中检查：

- 上一阶段输出能否直接成为下一阶段输入。
- 同一术语、对象、状态和单位是否一致。
- 每项评价指标是否有可获得的数据来源。
- 每个失败条件是否有负责人、动作和回退位置。
- 是否存在重复阶段、职责空白或循环依赖。
- 顶层目标是否能由最终输出和验收规则证明完成。

发现问题时记录冲突位置、影响、最小修正方案和需要重新打开的门槛。不得静默改写历史决定。
