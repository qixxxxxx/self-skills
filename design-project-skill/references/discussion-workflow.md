# 项目讨论、定稿与验收工作流

本文的一至七阶段是本 Skill 主持讨论和落地的元流程，不是目标 Skill 的业务阶段。初始化的九类覆盖门槛统一归入 `stage-design`；目标 Skill 自己的业务阶段只有在用户确认顶层流程后才写入 `stages/`。

## 目录

1. 总体原则
2. 阶段 1：状态初始化
3. 阶段 2：恢复与完整性入口
4. 阶段 3：定位层级和确认点
5. 阶段 4：讨论与软检查点
6. 阶段 5：确认与硬检查点
7. 阶段 6：门槛验收和阶段推进
8. 阶段 7：定稿、Skill 落地和用户验收
9. 从零设计覆盖门槛
10. 状态分类和评价顺序
11. 跨阶段一致性

## 一、总体原则

- 通过 `project-state.md` 定义的状态包恢复项目，不依赖聊天摘要重建决定。
- 每个有效回合先运行 `resume`；有活动事务时只处理该事务工作区。
- 先目标和边界，后顶层流程；先确认顶层流程，后展开阶段细则。
- 每轮只要求用户作出一个关键决定，但必须把该决定解释完整。
- 用户确认后先提交硬检查点，再把下一确认点交给用户。
- 新事实、建议、例子、假设、暂缓项或状态变化先提交软检查点，再输出项目讨论回复。
- 正常项目状态只按 `active/blocked → ready-for-build → building → awaiting-acceptance → completed` 前进；返回已确认设计或完成后再次修改使用 `reopen`。
- `ITEMS.md` 保存全部讨论项；任何遗留内容不能只留在旧 `ACTIVE.md` 或聊天中，既有条目不得删除，作废时保留为 `superseded` 并记录依据。
- 状态或语义不一致时冻结推进，保存现场并进入 T-09。

`user-interaction-templates.md` 是项目讨论最终回复的内容契约。Skill 使用公告、工具调用进度、文件写入提示和其他操作性 commentary 不属于项目讨论模板，不创建虚构检查点；宿主要求使用结构化提问工具时，把模板中的唯一问题映射到该工具。

## 二、阶段 1：状态初始化

### 输入

- 用户的初步需求、背景、资料和约束。
- 用户指定的状态包目录，或唯一明确的项目工作目录。

### 动作

1. 提取已明确的项目标题、目标摘要、使用者、输入、输出、范围、非目标和约束，不重复询问。
2. 目录未确认时使用 T-01；不得先创建状态包。
3. 检查目录身份和已有状态：
   - schema 2 且身份一致：进入恢复。
   - schema 1 且身份一致：说明迁移影响后运行 `migrate`。
   - 身份不一致或无法判断：停止并询问。
4. 新项目运行 `project_state.py init`，建立 schema 2 状态、`ITEMS.md`、事务元数据和 `v0000`。
5. 运行 `audit`。
6. 建立软事务，把用户已提供事实、首个问题的完整解释和总账更新到工作区，提交后使用 T-02 或 T-03。

### 完成条件

- 状态目录和项目身份唯一。
- `audit` 通过。
- `PROGRESS.md`、`ACTIVE.md` 和 `ITEMS.md` 指向同一问题。
- 首个问题具有完整说明，而不是初始化占位内容。

## 三、阶段 2：恢复与完整性入口

每个新回合、上下文压缩、跨时段继续、工具中断或记忆不确定时先运行：

```bash
/Users/lq/slot_math_env/bin/python "<skill-dir>/scripts/project_state.py" resume \
  --state-dir "/absolute/path"
```

### 路由

- 状态有效且无活动事务：读取 `PROGRESS.md`、`ACTIVE.md` 和当前 `ITEMS.md` 项目。
- 存在 `preparing` 事务：继续命令返回的唯一 `work/`，不重新创建事务。
- journal revision 领先或现行文件未完整落盘：冻结讨论并运行 `recover`；journal 缺失/损坏但 manifest 与现行状态可信时运行 `repair`；两侧都不能证明时保留现场并等待人工决定。处理前使用 T-09。
- 用户要求修改历史规则：完整读取相关决定、阶段和版本，然后使用 `reopen`。
- 即将硬提交、阶段切换、全局定稿或 Skill 落地：执行完整 `audit` 和语义检查。

完整恢复只读取当前目标、直接依赖阶段、相关决定和当前正式版本；不机械加载全部历史。

### 输出

- 只查询状态：T-07。
- 首次恢复、压缩后继续或需要回顾依据：T-08。
- 任一检查失败：T-09。

## 四、阶段 3：定位层级和确认点

1. 从 `ITEMS.md` 选择最高层、必需、未终结且阻断后续工作的项目。
2. 目标和边界未确认时，不展开顶层流程。
3. 顶层流程未确认时，不填充阶段细则。
4. 顶层流程通常保持 4～8 个阶段；超过时检查是否混入子步骤。
5. 当前问题必须说明：
   - 具体确认什么。
   - 为什么现在确认。
   - 会影响哪些后续门槛。
   - 采用后的实际过程。
   - 正常、边界和异常例子。
6. 阶段复杂时先拆成 3～7 个子流程，但本轮仍只确认一个关键决定。
7. 顶层流程足以判断复杂度后，读取 `template-definition-standard.md`，暂定或确认目标 Skill 为简单、标准或复杂多阶段，并记录判定依据；不因本设计流程本身复杂而默认升级目标 Skill。
8. 报告、清单、固定文档或目录型知识按已选等级讨论；只有字段或治理选择会改变范围、评价、责任、成本或风险时才新增确认点。
9. 算法、评分、权重、概率、阈值、分类、排序、迭代或自动回退读取 `human-readable-explanations.md`。

如果当前问题依赖未确认的上层决定，取消该问题的活动状态，重新打开上层项目并提交软检查点。

## 五、阶段 4：讨论与软检查点

### 内容分类

把本轮内容分成：已知事实、已确认、AI 建议、待确认、临时假设、暂缓、不适用和阻塞。

### 提交流程

1. 运行 `begin --kind soft`。
2. 只编辑事务 `work/` 中的 `ACTIVE.md`、`ITEMS.md` 和必要的 `PROGRESS.md`。
3. `ACTIVE.md` 保存当前问题的背景、规则、适用范围、实际过程、例子、影响、代价、建议和确认边界。
4. `ITEMS.md` 保存所有新增事实索引、假设、暂缓项、阻塞和后续问题。
5. 输出规则同时保存已选治理等级及对应契约；简单等级不得被迫补齐复杂报告基础设施，复杂等级的机器事实、阶段身份、证据和复算要求不得只留在聊天中。
6. 运行 `commit`；提交失败时使用 T-09，不输出成功状态。
7. 单一建议使用 T-02；存在 2～3 个实质方案使用 T-03；用户回复有附加条件或歧义使用 T-04。

纯状态查询或没有新内容的只读说明不创建软事务。校验发现缺失、冲突或状态变化时仍必须落档。

### 完成条件

- 用户不依赖旧聊天也能理解当前问题。
- 正式规则没有混入未确认建议。
- 用户确认后可以直接硬提交，不需要 AI 猜测关键细节。
- 所有非当前讨论项已经进入总账。

## 六、阶段 5：确认与硬检查点

### 进入条件

用户明确确认当前完整规则，或直接提供无歧义正式规则。模糊认可、部分接受或附带新条件继续使用软检查点。

### 提交流程

1. 运行 `begin --kind hard`；修改已确认规则使用 `reopen`。
2. 在事务工作区关闭原 `Q` 项，在 `DECISIONS.md` 写入决定正文，并在 `ITEMS.md` 登记同编号 `decision` 条目、证据和被替代关系。
3. 更新 `PROJECT.md`、`DECISIONS.md`、相关阶段文件和门槛。
4. 把仍未确认的假设、暂缓项和后续问题保留在 `ITEMS.md`。
5. 除最终项目完成外，建立唯一下一问题。
6. 在新的 `ACTIVE.md` 中完整准备下一确认点，至少达到其应有的 L2/L3 深度。
7. 运行 `commit`；脚本自动生成新版本快照并执行 audit。

问题的 `confirmed/completed`、门槛的 `completed/not-applicable/superseded` 都必须引用本次或已有的真实决定/证据。关闭当前问题时必须引用本次新增决定；该决定按确认前 `ACTIVE.md` 的 L2/L3 深度保留实际过程和相应例子。不得用旧决定、`ACTIVE.md`、“待用户确认”或没有正文的决定编号充当本轮终结依据。

### 输出

- 阶段未完成：T-05。先从本次新增决定逐节恢复刚确认规则：L2 至少展示决定、实际过程、正常例子、证据和影响；L3 继续展示边界例子和异常例子。然后完整展示下一确认点。两个区块任一不完整时不得输出 T-05 成功状态。
- 阶段最后门槛关闭：T-06。T-06 必须包含下一阶段首个问题的完整说明。
- 用户对新确认点的回复再按 T-02/T-03/T-04/T-05 路由。

## 七、阶段 6：门槛验收和阶段推进

门槛以 `ITEMS.md` 中 `type=gate` 的项目为唯一计数来源。每个门槛保存完成条件、证据、状态、责任人、依赖和重开记录。

规则：

- 只有具有有效证据的 `completed` 门槛计入完成。
- `not-applicable` 和 `superseded` 不计入分母，但必须有决定依据。
- 门槛处于 `confirmed` 仍未完成，不能用于阶段、定稿或项目完成。
- 新增范围时新增门槛；重新打开后立即移出完成数。
- 阶段全部必需门槛关闭后，检查输出能否成为下一阶段输入。
- 任何阶段不能用其他阶段的超额完成抵消缺失门槛。

阶段状态固定为：未开始、讨论中、等待确认、已确认、阻塞、重新打开、已完成。

## 八、阶段 7：定稿、Skill 落地和用户验收

### 全局定稿

1. 检查目标、范围、顶层流程、阶段契约、评价、异常、回退和责任边界。
2. 检查治理等级与真实复杂度一致：简单 Skill 没有无用途的目录、Hash、生成器或分册；复杂多阶段 Skill 的事实源、报告、门禁、Owner和复算链没有缺口。
3. 关闭全部关键门槛；非关键保留项必须进入 `ITEMS.md` 且不会改变主体设计。
4. 在请求落地授权前，分别确认目标 Skill 名称和绝对目录。
5. 名称或目录未确定时继续使用 T-02/T-03，不得使用 T-10。
6. 全局 audit 和语义检查通过后，在关闭最后设计门槛的硬事务或紧随其后的软事务中设置 `project_status=ready-for-build`，并建立唯一授权问题，再使用 T-10 请求一次明确落地授权。

### Skill 落地

1. 用户授权后硬提交授权决定，把 `project_status` 改为 `building`。
2. 读取 `skill-finalization.md` 和 `skill-creator`，创建或更新目标 Skill。
3. 运行结构、脚本、正向、边界、层级、恢复和独立前向测试。
4. 验证通过后硬提交 `project_status=awaiting-acceptance`，建立唯一用户验收问题，使用 T-11。

### 用户验收

- 用户接受：硬提交验收决定，关闭全部必需项目，设置 `project_status=completed`、`current_question=none`，运行 `finish`，使用 T-12。
- 用户要求修改：使用 `reopen` 重新打开最小必要门槛，保留已生成文件和验证证据，回到 T-02/T-03。
- 用户拒绝落地：保持定稿状态，不创建目标 Skill，也不把项目标记完成。

## 九、从零设计覆盖门槛

从零设计新 Skill 时，以下主题都必须确认或明确标记不适用：

1. **目标与使用者**：解决什么问题、谁使用、成功标准、非目标。
2. **触发边界**：典型触发语句、明确不触发的场景、正反例。
3. **输入输出**：输入资料、输出形态、治理等级、固定模板、数据来源、空值规则；目录型知识是否需要机器事实源、中文介绍和生成式汇总。
4. **工具环境**：依赖工具、运行环境、权限、外部系统和资料目录。
5. **流程状态**：顶层流程、阶段契约、状态变化、唯一下一动作和责任边界。
6. **安全副作用**：外部写入、不可逆操作、并发、敏感数据和停止条件。
7. **异常兼容**：失败恢复、重试、回退、兼容性、迁移和性能约束。
8. **验证维护**：正向、边界、异常、恢复、前向测试、最终验收和后续维护方式。
9. **Skill 包装**：名称、description、目录、references、scripts、assets 和 agents 元数据。

这些主题是覆盖门槛，不是一次性问卷。一次只讨论当前最上层、最阻断后续工作的决定。

## 十、状态分类和评价顺序

| 状态 | 含义 |
|---|---|
| 已知事实 | 来自用户、资料或已验证现场 |
| 已确认 | 用户明确接受并已进入硬检查点 |
| AI 建议 | 尚未获得用户确认的方案 |
| 待确认 | 会影响后续设计，必须取得答案 |
| 临时假设 | 暂时采用，具有明确替换条件 |
| 暂缓 | 当前版本不决定，但保留原因和重新打开条件 |
| 不适用 | 已证明不适用于本项目并记录依据 |

评价按“评价对象 → 指标和数据 → 算法 → 基准和容差 → 权重/阈值 → 判定 → 结果解释”建立。综合得分不能覆盖最低通过要求，总结果必须追溯到具体阶段、指标和差距。

## 十一、跨阶段一致性

集中检查：

- 前一步输出能否直接成为后一步输入。
- 同一术语、对象、状态、单位和字段顺序是否一致。
- 目标 Skill 的治理等级是否与阶段依赖、报告风险、目录规模和复算要求一致。
- 每项评价指标是否有可获得的数据来源和计算方法。
- 每个失败条件是否有负责人、动作和回退位置。
- 是否存在重复阶段、职责空白、循环依赖或未授权副作用。
- 所有必需讨论项是否终结，非关键保留项是否有落点。
- 最终输出和用户验收能否共同证明顶层目标完成。

发现问题时记录冲突、影响、最小修正方案和需要重新打开的门槛，不静默改写历史决定。
