# 项目讨论与定稿工作流

## 一、启动讨论

先从用户已提供的信息中提取项目名称、背景、期望结果和现有资料，不重复询问已经明确的内容。信息不足时，每轮只询问当前推进所必需的一个关键问题；若可以做低风险假设，应明确标注为“临时假设”，并继续推进。

首次讨论建议形成一个简短项目卡片：

| 项目项 | 需要明确的内容 |
|---|---|
| 项目目标 | 最终希望解决什么问题、得到什么结果 |
| 使用者 | 谁会执行流程、谁消费结果 |
| 输入 | 用户会提供哪些资料、数据或初始条件 |
| 输出 | 最终交付什么文档、配置、代码、结论或 Skill |
| 范围 | 本项目包含哪些工作 |
| 非目标 | 明确暂时不做什么 |
| 约束 | 时间、工具、目录、权限、质量或合规限制 |

不要在本阶段直接展开所有细则。

## 二、确认顶层流程

根据目标提出最少且完整的顶层阶段，每个阶段只用一段话说明“解决什么问题、产出什么结果”，暂不写字段、算法或操作步骤。通常保持在 4～8 个阶段；如果更多，应检查是否混入了子步骤。

顶层流程至少应覆盖以下职责，但名称和组合要根据项目调整：

1. 识别项目与收集输入。
2. 确认资料、对象或数据的数量、结构和完整性。
3. 建立分类、术语和适用规则。
4. 定义需要对齐、实现或交付的目标及评价标准。
5. 执行分析、设计或实现。
6. 评分、验收并定位差距。
7. 调整、复验和交付。

评分位于评价对象和规则已经定义之后、调整之前。采集数量与结构确认位于输入收集之后、正式分析之前。

把顶层流程交给用户确认。用户要求“更上层”时，只合并阶段和压缩描述，不增加细节。

## 三、逐阶段讨论

顶层流程确认后，一次只讨论一个阶段。按需使用下表，不必在第一次讨论中机械填满全部字段。

| 阶段项 | 要回答的问题 |
|---|---|
| 阶段目标 | 这一阶段必须解决什么问题 |
| 输入 | 从哪里获得什么内容，最低完整性是什么 |
| 前置条件 | 满足什么条件才能开始 |
| 核心动作 | 执行哪些必要动作，先后和依赖是什么 |
| 分类与规则 | 不同对象应匹配哪些规则，哪些规则通用或专用 |
| 输出 | 产出什么，格式和必要字段是什么 |
| 完成条件 | 如何判断本阶段完成并可进入下一阶段 |
| 评价方式 | 用哪些指标、阈值、权重或人工判断验收 |
| 异常与回退 | 缺失、冲突或失败时怎么处理，回到哪一步 |
| 责任边界 | AI、用户、脚本或外部系统分别负责什么 |

阶段较复杂时，先拆为 3～7 个子流程，再逐个讨论；不要把所有细则塞进同一张表。

## 四、比较方案并做决定

存在多种合理方案时，最多先给 2～3 个选项，说明适用条件、主要收益和代价，并给出有依据的推荐。只有会显著改变范围、成本、输出或风险的选择才要求用户决定。

使用以下状态区分内容：

| 状态 | 含义 |
|---|---|
| 已知事实 | 来自用户、资料或已验证结果 |
| 已确认 | 用户已经明确接受的设计 |
| AI 建议 | 尚未获得用户确认的方案 |
| 待确认 | 会影响后续设计，必须取得答案 |
| 临时假设 | 为继续推进而采用，可被后续证据替换 |
| 暂缓/不适用 | 本版本不处理，但保留原因 |

每轮结束时，用简短内容汇总“本轮结论、待确认的一点、确认后的下一步”。

## 五、建立评价与验收

先定义评价对象，再定义指标和算法，最后确定权重、阈值、评分区间或通过规则。不得先给总分再反推指标。

评价体系至少回答：

- 评什么：流程结果、数据质量、实现质量、体验差距或交付完整性。
- 怎么量：计算方法、数据范围、样本要求和单位。
- 怎么比：基准值、容差、权重和聚合方式。
- 怎么判：通过、需调整、阻断分别满足什么条件。
- 怎么解释：总分必须能追溯到具体阶段和差距项。

如果当前阶段只需“对齐指标”，不要提前加入稳定性评分、置信度或优先级模型；把它们记录为后续评价层候选项。

## 六、跨阶段一致性检查

全部阶段初稿形成后，集中检查：

- 上一阶段输出能否直接成为下一阶段输入。
- 同一术语、对象、状态和单位是否前后一致。
- 每项评价指标是否有可获得的数据来源。
- 每个失败条件是否有处理人、处理动作和回退位置。
- 是否存在重复阶段、职责空白或循环依赖。
- 顶层目标是否能由最终输出和验收规则证明完成。

发现问题时指出冲突位置、影响和最小修正方案，回到相应阶段更新，不要静默改写已确认决定。

## 七、版本化文档

用户未指定时，建议至少维护以下逻辑内容，可合并为一份文档，也可分文件：

- 项目说明：目标、范围、输入输出和约束。
- 顶层流程：阶段、顺序和阶段产出。
- 阶段细则：阶段契约、分类规则和异常处理。
- 评价验收：指标、评分、阈值和复验规则。
- 决策记录：变更原因、替代方案和未决项。

更新已有文档时遵守：

1. 将用户指定的原始文件视为只读基线。
2. 创建递增版本，例如 `name-v1.md`、`name-v2.md`；沿用项目已有命名规则时优先遵循项目规则。
3. 新版本顶部记录版本号、基于哪个版本、变更摘要和仍待确认内容。
4. 不把未确认建议混入正式规则；可放入“待确认”章节。
5. 用户确认新版本后，再把其中的决定标为当前有效版本。

## 八、讨论完成总结

在进入 Skill 制作前输出定稿摘要：

- 项目目标、范围与非目标。
- 已确认的顶层流程。
- 各阶段的核心输入、输出和完成条件。
- 分类和适用规则。
- 评价、验收、异常与回退机制。
- 当前有效文档版本。
- 已关闭和仍保留的待确认项。

最后明确询问用户是否进入 Skill 落地阶段。未得到明确同意时继续讨论或停留在定稿状态。
