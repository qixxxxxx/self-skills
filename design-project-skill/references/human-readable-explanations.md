## 一、目标与边界

内部状态文件可以保留专业字段、编号和精确规则；用户可见回复必须翻译成普通人能够理解、复述和判断的语言。

“详细”不等于堆砌术语或拉长篇幅。一个说明达到要求，意味着用户能够回答：

- 现在要决定什么。
- 为什么需要决定。
- 实际运行时先做什么、后做什么。
- 正常情况下会得到什么结果。
- 特殊或失败情况下怎么办。
- 自己确认后会改变什么。

每轮只确认一个关键问题，是限制问题数量，不是限制该问题的解释深度。

## 二、普通语言规则

- 先说结论，再解释原因和细节。
- 使用短句；一段只表达一个主要意思。
- 能用日常表达时不直接使用专业术语。
- 专业词第一次出现时，先用普通话解释，再在括号中给出术语。
- 不连续堆叠缩写、英文名或内部编号。
- 从用户会看到什么、需要做什么、会得到什么结果来解释规则。
- 抽象规则至少配一个具体场景。
- 复杂规则至少包含正常、边界和异常三种情况。
- 数字、比例、权重、阈值或概率必须配合小数字演算或数量例子。
- 先讲例子，再总结规则；先讲规则含义，再给公式。
- 不用固定字数判断详细程度，避免为了变长而重复。

不推荐：

```text
本决定会改变下游阶段输入契约和验收门槛。
```

推荐：

```text
如果采用这个方案，下一步收集的数据格式就会固定下来。以后新增字段时，之前的统计结果可能需要重新计算，所以要在现在把字段范围定清楚。
```

## 三、讨论深度等级

深度等级用于内部选择，不要求在用户回复中显示等级代码。

| 等级 | 使用场景 | 最低要求 |
|---|---|---|
| L1 简洁 | 状态查询、单点澄清、无规则变化 | 结论、状态、当前问题或下一步 |
| L2 标准 | 普通阶段规则、单一方案确认 | 背景、规则、适用范围、实际过程、正常例子、边界、影响、建议 |
| L3 深入 | 目标、范围、顶层流程、跨阶段规则、架构、评价、算法、回退 | 完整决策内容、正常/边界/异常场景、依赖、替代方案、验收影响和可复算示例 |

默认规则：

- T-01、T-04、T-07 通常使用 L1。
- T-02 默认使用 L2；涉及跨阶段或重大规则时使用 L3。
- T-03 默认使用 L2；比较算法、评价模型或重大架构时使用 L3。
- T-05 必须保留刚确认规则对应的解释深度，不能压缩成一句摘要。
- T-08 恢复时至少恢复当前确认点原来的解释深度。
- 算法、评分、权重、概率、阈值、分类、排序、迭代调参和自动回退至少使用 L3。
- 用户明确要求更简短时可以降低表达长度，但不能省略会改变理解或决定的关键事实。

## 四、完整决策内容

L2 或 L3 确认点应按实际需要回答以下内容。用户确认后，如果仍需 AI 猜测关键规则，说明讨论还不完整。

1. **已知背景**：哪些事实、约束和旧决定已经确定。
2. **本轮问题**：具体确认哪一条规则，不混入其他决定。
3. **现在确认的原因**：它阻断了哪些后续工作。
4. **规则正文**：采用后系统、用户或流程实际怎么做。
5. **适用范围**：什么情况下生效。
6. **不适用范围**：什么情况不按这条规则处理。
7. **前置条件**：开始前必须具备什么。
8. **执行过程**：先做什么、再做什么、最后得到什么。
9. **正常例子**：常规情况下完整走一遍。
10. **边界例子**：刚好达到条件、刚好不满足或数据不完整时如何处理。
11. **异常例子**：失败、冲突或不可恢复时怎么办。
12. **影响**：用户操作、后续阶段、文件、数据、成本和维护有什么变化。
13. **替代方案**：如果存在合理选择，说明差异和不推荐原因。
14. **验收变化**：确认后关闭、增加或重新打开哪些完成事项。
15. **确认边界**：本轮确认什么，明确不确认什么。

## 五、常见术语翻译

| 专业表达 | 用户可见表达 |
|---|---|
| 阶段门槛 | 这一阶段必须完成的事项 |
| 输入输出契约 | 这一步需要什么资料，完成后交给下一步什么结果 |
| 上游/下游 | 前一步/后一步 |
| 阈值 | 达到多少才算通过 |
| 权重 | 这一项在最终结果中占多大影响 |
| 回退机制 | 失败后退回哪一步，以及保留什么 |
| 语义一致性 | 前后说的是不是同一件事 |
| 幂等 | 重复执行不会产生重复结果 |
| 置信度 | 对当前判断有多大把握 |
| 聚合 | 把多个结果合成一个结果 |
| 校准 | 根据真实结果调整计算方式 |

术语确实有助于后续精确讨论时，可以在普通解释后保留，例如：

```text
这一步失败后要退回到数据确认阶段，同时保留已经验证过的资料。后文把这套处理简称为“回退机制”。
```

## 六、算法说明顺序

涉及算法、评分或公式时，必须按以下顺序表达：

1. **算法想解决什么问题**：先说业务问题，不先报算法名称。
2. **一句话说明做法**：用日常语言概括判断方法。
3. **需要哪些数据**：列出输入及单位，说明由谁提供。
4. **实际执行步骤**：按 1、2、3 展示计算或判断顺序。
5. **小数字例子**：使用 2～3 个对象和容易心算的数字。
6. **结果含义**：解释数字高低、通过失败或分类结果代表什么。
7. **边界和异常**：数据缺失、并列、低于最低要求、超出范围时怎么办。
8. **主要代价和限制**：说明算法不能证明什么、可能偏向什么。
9. **最后给公式或伪代码**：公式是例子的总结，不是解释的起点。
10. **确认内容**：明确用户是在确认输入、权重、阈值、计算方法还是判定规则。

每个公式中的符号、单位和取值范围都要解释。不能只给计算结果而不解释结果如何影响实际决定。

## 七、算法示例要求

| 类型 | 至少提供的例子 |
|---|---|
| 加权评分 | 两个方案的分项得分、逐项乘权重和最终合计 |
| 阈值判断 | 明显通过、刚好通过、刚好不通过三个情况 |
| 概率 | 换算成 100 次中大约发生多少次，并说明不是固定频率保证 |
| 排序 | 排序前数据、比较依据和排序后结果 |
| 分类 | 至少三个对象，说明为什么进入不同类别 |
| 条件流程 | 使用“如果……那么……”走完正常和异常分支 |
| 迭代调整 | 展示第一次、第二次、第三次如何逐步接近目标 |
| 自动回退 | 模拟某一步失败后退回哪里、保留什么和重新执行什么 |

例子必须与当前项目对象一致。不能用完全无关的通用例子代替真实规则。

## 八、典型示例

### 加权评分

要解决的问题：在质量和成本之间选择更合适的方案。

普通解释：质量更重要，所以质量占最终结果的 60%，成本占 40%。

方案 A：

- 质量 80 分。
- 成本 50 分。
- 质量部分：`80 × 60% = 48`。
- 成本部分：`50 × 40% = 20`。
- 最终结果：`48 + 20 = 68` 分。

方案 B：

- 质量 70 分。
- 成本 90 分。
- 质量部分：`70 × 60% = 42`。
- 成本部分：`90 × 40% = 36`。
- 最终结果：`42 + 36 = 78` 分。

结果解释：方案 B 的综合结果更高，但如果质量的最低通过要求是 75 分，方案 B 仍然不能通过。综合得分和最低要求是两条不同规则，需要分别确认。

最后再给公式：

```text
最终分数 = 质量分 × 质量权重 + 成本分 × 成本权重
```

### 概率

不推荐：

```text
失败概率为 20%。
```

推荐：

```text
按照当前估算，如果类似情况发生 100 次，大约有 20 次可能失败、80 次正常完成。这不代表每 5 次一定失败 1 次，而是长期情况下的大致比例。
```

### 阈值

假设最低通过要求是 75 分：

- 82 分：明显通过。
- 75 分：刚好通过。
- 74 分：刚好不通过。

还要说明分数缺失、计算异常或人工复核时是否允许例外。

## 九、状态落档要求

软检查点中的 `ACTIVE.md` 应保存：

- 当前选用的解释深度。
- 面向用户的普通语言规则。
- 正常、边界和异常例子。
- 算法输入、步骤、示例计算、结果含义和限制。
- 用户本轮实际需要确认的内容。

硬检查点中的 `DECISIONS.md` 和正式规则应保留：

- 用户确认时看到的完整规则，不压缩成一句结论。
- 确认过的例子和边界。
- 权重、阈值、单位、公式和判定顺序。
- 用户确认的部分与仍未确认的部分。

这样恢复时可以重新展示相同含义，而不是根据一句摘要重新推测。

## 十、输出验收

输出前检查：

- 不熟悉项目的人能否说出现在要决定什么。
- 用户能否根据例子预测另一个相似案例的结果。
- 专业词是否已经用普通语言解释。
- 数字、权重、阈值、概率和公式是否有具体例子。
- 是否说明正常、边界和异常情况。
- 是否说明采用方案后的实际变化和主要代价。
- 推荐理由是否来自现有目标和约束。
- 用户确认后能否直接正式落档，不需要 AI 再补猜关键内容。
- 最后问题是否只要求一个清楚决定。

任一关键项不满足时，补充说明后再询问用户。不要用“用户可以后续再看细节”代替本轮必要解释。
