# 阶段 1：资料确认与玩法画像

## 输入门禁

同时确认：游戏规则/规格、原版采集协议、`mode × rtp_group`、权威目标 RTP、Runtime、模拟脚本、server 对齐证据、工作区路径、参数授权。任一必需项缺失或不唯一时标记`阻塞`。

原版协议先归一化为逐个完整付费入口链：一次真实扣款开始，包含其自然触发的全部后续状态，直到返回可再次扣款的稳定状态。定向 Feature 样本只能用于玩法内部诊断，不得混入总体 RTP、中奖率、自然触发率、总局倍率分布或总体 Sigma。

按统一付费入口口径拆分 Base、Feature 和其他组件派奖，计算每个组件占原版总派奖的贡献占比。原版组件绝对 RTP 只保留为诊断证据；阶段 2 必须用贡献占比映射权威总 RTP 目标，不能直接复制原版绝对 RTP。

## 脚本资格

阶段 1 只执行一个密封的 server flow 一致性认证批次。该批次可包含多条固定种子或 RNG trace，用于覆盖输入作用域、RNG 顺序、状态转移、触发、重触、collect、结算、封顶、金额守恒及统计口径，但不得在后续阶段、候选或样本间重复完整调用。

模拟脚本只有基础逻辑和输出不足时，可只增强观测字段；不得改变游戏结果。修改后必须回到阶段 1，以新的密封输入版本重新建立唯一认证批次。认证通过后，阶段 2～5、CALIBRATION 和 FORMAL 统一使用该已认证模拟路径，server flow 调用数必须为 0。

## 玩法画像生成

1. 从规则、协议字段、状态链、server/Python 实现提取事实。
2. 查询`mechanics/index.json`，只用稳定`mechanic_id`和标准属性表达，不用自由文本名称匹配指标。
3. 每个画像节点记录证据路径、证据类型、作用域、必需性、置信状态和父子关系。
4. 未找到语义时标记`语义缺口`，停止阶段 1 并形成扩展提案；不得临时发明 ID。
5. 同一玩法识别为同一`mechanic_id`后，含义由语义包版本与 hash 固定；游戏专属差异写入标准属性。

## 参数权限与控制拓扑

逐项登记参数路径、类型、合法范围、是否可调、预计影响的随机源/状态、耦合关系和禁止原因。结构参数、玩法开关、状态机、触发/结算公式、RNG 顺序和封顶均默认禁止。

## 固定输出

```text
artifacts/01-input-profile/
├── input_manifest.json
├── game_profile.json
├── parameter_authority.json
└── 阶段1-资料确认与玩法画像.md
```

机器 JSON 是权威事实，中文 Markdown 汇总三份 JSON，重点展开玩法画像、证据和参数边界。使用`assets/templates/artifacts/01-input-profile/`中的固定模板。

中文报告必须运行`render_input_profile_report.py`生成，并严格使用阶段1模板的11章结构。每章按模板规定的展示方式、字段顺序、空值规则和Markdown实例输出。不得只写结论摘要；必须逐项呈现输入及hash、排除样本、完整付费入口口径、原版样本批次、组件贡献占比、玩法树和节点、执行链一致性、参数权限、数据门禁、阻塞恢复和阶段2准入。

## 完成条件

- 所有输入 hash 和作用域已密封；金额与付费入口口径有效。
- 原版组件贡献占比可复算、合计为 1，并绑定合格样本及 hash。
- 模拟脚本具有当前版本 FORMAL 资格，或明确阻塞原因。
- `script_qualification.server_flow_certification`状态为`通过`、认证批次数为 1，并覆盖全部关键状态链；阶段 1 之后不得再次调用 server flow。
- 必需玩法节点均有稳定语义 Owner，无语义缺口。
- 所有可调参数获得明确授权且不会改变玩法规则。
