## 标准目录ID

跨项目路径只允许使用下列ID：

| ID | 用途 | 固定分支或环境 |
|---|---|---|
| `config-test` | 测试Runtime配置仓库 | `main` |
| `config-prod` | 正式Runtime配置工作树 | `release` |
| `slot-docs` | 规格、玩法、接口和资料 | `main` |
| `slot-math-workbench` | 原版采集、模拟、对齐和归档 | `slot-docs`内工作区 |
| `pragmatic-workbench` | Pragmatic协议、资源、Mock和工具 | `main` |
| `server-dev` | 开发服务端与测试Runtime缓存 | `dev` |
| `server-prod` | 正式服务端工作树与正式Runtime缓存 | `release` |

非绝对项目路径统一写成：

```text
<directory-id>:<relative-path>
```

示例：

```text
slot-docs:<game_code>/math/scripts/
slot-math-workbench:<game_code>/capture-summary/
config-test:pragmatic/<game_code>/
config-prod:pragmatic/<game_code>/
server-dev:config-package-cache/main/<game_code>/<hash>/
server-prod:config-package-cache/release/<game_code>/<hash>/
pragmatic-workbench:<game_code>/
```

- `runtime_environment=test`只配对`config-test + server-dev`。
- `runtime_environment=prod`只配对`config-prod + server-prod`。
- 不允许拼写变体、自定义根变量或测试/正式混用。
- 从项目`AGENTS.md`的`directories`映射解析绝对路径。
- 通用合同和报告保存目录ID路径；机器manifest可额外保存绝对解析路径和hash，便于本机复算。

## 任务根目录

每个目录只代表一次独立对齐任务：

```text
slot-math-workbench:<game_code>/alignments/<mode>/<task_id>/
```

`task_id`格式为`aln-<mode>-<YYYYMMDD>-<NNN>`，只使用小写字母、数字和连字符。创建前确认目录不存在。

以下变化必须新建`task_id`：

- 模式变化；
- 已完成任务重新对齐；
- 用户确认RTP变化；
- 玩法或指标作用域实质变化；
- 需要同时保留变化前后结果的Runtime大版本变化。

Runtime版本不单独编号：

```text
game_core.json.meta.version = task_id
delivery_manifest.runtime_version = task_id
rtp_group = 1
```

## 目录职责

| 目录 | 负责 | 禁止放入 |
|---|---|---|
| `artifacts/` | 五阶段唯一权威机器JSON | Markdown、分片、临时文件、候选Runtime和重复结果 |
| `work/` | 密封Runtime、分片、checkpoint、敏感性、候选、冻结、FORMAL和阶段报告 | 最终权威合同的替代副本 |
| `scripts/` | 当前游戏的模拟、观测、候选生成和流程适配脚本 | `slot-alignment`通用脚本的复制品 |
| `交付物/runtime/` | FORMAL实际验收的Runtime四件套 | 非FORMAL候选 |
| `交付物/报告文档/` | 唯一最终`对齐报告.md`及其机器校验清单 | 其他Markdown、版本目录、候选参数和未替换占位 |

`work/`可以复算或续跑，但不能替代`artifacts/`。报告只能读取权威机器JSON，不能反向修改机器结果。

## 机器JSON合同

- `workspace_layout_policy.json`逐项绑定权威产物、过程记录、Schema和模板；Markdown目录树不得单独增加机器文件。
- `input_manifest.json`同时保存稳定`game_code`和报告使用的`game_name_zh`，避免最终报告从目录名或技术ID猜游戏名称。
- 原版目标证据不另建重复文件：`targets.json`保存逐实例目标状态和样本计数，`metric_contract.json`冻结活动/观察决定、覆盖计数和政策hash。
- `artifacts/`内每个JSON必须通过绑定Schema。`work/`中明确命名的计划、manifest、参数记录、分片、测量和结果同样必须通过绑定Schema。
- `work/script-equivalence/`中的原始日志、差异文件和有界事件样本可以不是JSON；它们必须由`script_equivalence.json`记录路径与SHA-256。
- 所有`runtime/`目录都固定包含`game_core.json`、`payout_config.json`、`reel_config.json`和`symbol_catalog.json`，不得只复制部分文件。
- 候选搜索明细只由各`batch_manifest.json`保存，冻结复核与FORMAL批次只由`alignment_manifest.json`统一索引；交付检查只保存在`delivery_manifest.json.checks`，报告来源与文件检查只保存在唯一`report_manifest.json`，不建立第二份检查事实源。

## 产物晋级

1. 阶段1和2的权威结果直接写入对应`artifacts/`目录，并立即通过绑定Schema。目标证据决策随`metric_contract.json`一次冻结，候选出现后不得原地改角色。
2. BASELINE先在`work/baseline/`完成分片与聚合；`work/baseline/measurements.json`校验通过后，原样晋级为`artifacts/03-evaluation/baseline_measurements.json`，两者SHA-256必须一致。
3. 每个CALIBRATION批次只写入一个新的`cv####/`。候选明细保留在候选目录，批次排序与晋级依据保存在`batch_manifest.json`。
4. 决赛前2名先把参数记录和Runtime复制到各自的`candidate-freeze/`，再在其中另跑200万独立复核；复核完成后由`freeze_manifest.json`绑定合同、脚本、能力矩阵和结果。`alignment_manifest.json.candidate_freezes`索引全部实际复核候选，并且只标记一个FORMAL入选候选。
5. 每次FORMAL只写入一个新的`fv####/`，失败批次永久保留。`formal_plan.json`在运行前冻结全部逻辑分片，`alignment_manifest.json.formal_batches`索引全部批次并只标记一个晋级批次。
6. 标记`promoted_to_artifact=true`的`work/formal/fv####/alignment_result.json`原样晋级为`artifacts/04-alignment/formal_result.json`，两者SHA-256必须一致。
7. `aligned_parameters.json`只保存冻结候选的最终完整参数，并绑定原始`parameter_record.json`与`freeze_manifest.json`的SHA-256。
8. `交付物/runtime/`逐文件复制选中FORMAL批次实际使用的Runtime；来源路径、来源hash和交付hash统一由`delivery_manifest.json`绑定。
9. 阶段3不生成Markdown。阶段5由当前`input_manifest.json`、`metric_contract.json`和`formal_result.json`原子生成`交付物/报告文档/对齐报告.md`。
10. `report_manifest.json`只绑定上述三份机器来源和唯一报告的SHA-256。报告需要重建时原子替换同一文件，不再建立其他阅读文件或版本目录。

## 命名、路径与写入

- 机器文件使用英文`snake_case`；稳定ID使用小写字母、数字、点和连字符。
- CALIBRATION批次使用`cv####`，FORMAL批次使用`fv####`。报告不单独编号。
- 分片文件固定使用`shard-######.json`，编号从`000000`开始，并与文件内`shard_index`一致。
- 任务内部机器路径一律相对任务根目录；外部输入至少保存目录ID路径和SHA-256。
- 时间使用带时区ISO 8601；概率和RTP使用`0～1`。
- `sample_execution_plan.json`必须在候选出现前冻结，并由`metric_contract.json`绑定hash。
- 每个逻辑分片同时保存聚合结果和累计器checkpoint，不再建立第二套checkpoint文件。
- 原子写入机器文件：先写同目录临时文件，校验成功后替换目标文件。临时文件不进入manifest，半成品不得标记完成。
- 不在`artifacts/`写Markdown，不在报告目录保存Runtime，不在任务根目录散落阶段文件。
- `交付物/报告文档/`内只能存在一份Markdown，文件名固定为`对齐报告.md`；N/J/P/B全部指标详情必须写入该文件。
- 使用`scripts/validate_workspace_layout.py --task-root <任务根目录> --through-stage <1-5>`校验当前阶段的目录、Schema、Runtime四件套和晋级hash。
- 冻结合同后不得原地修改目标、活动/观察角色、实例、距离算法、C级通过值、档位或样本计划。需要改变时使已有结果失效并重新生成。
- 不批量删除任务产物。明确废弃的单个文件只在用户授权后按完整路径单独处理。
