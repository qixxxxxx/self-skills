# 阶段 4：自动对齐与 FORMAL

## 生命周期

0. **阶段转换**：读取`artifacts/03-scoring/stage3_gate.json`，只有`status=通过`且`stage4_allowed=true`才能启动本阶段。
1. **基线继承**：使用阶段3已密封的当前 Runtime 基线；已达标则直接冻结，不为追求更高分增加变更。
2. **敏感性**：按控制簇做低成本合法扰动，确认参数生效、方向、耦合和局部有效秩。
3. **CALIBRATION**：在授权空间内使用安全漏斗搜索。
4. **候选冻结**：保存不可变候选 ID、完整参数、父候选、输入 hash、样本范围和评分。
5. **FORMAL**：使用预先密封且与 CALIBRATION 完全独立的新种子、新样本验收。

优化采用字典序：未豁免硬指标全部通过 → 综合分最高且至少 80 → 参数变化最小 → 长尾及运行风险最低。不得用后项补偿前项。

## 搜索边界

阶段4所有候选必须记录`stage3_gate.json`的SHA-256。门禁文件或其任一上游hash变化时，已有阶段4候选全部失效并退回阶段3重新评分和生成报告。

只修改授权参数并保持合法约束、归一化和依赖关系。参数未生效、控制方向与预检相反或游戏逻辑变化时立即隔离结果并退回阶段 1/2。

同轮候选使用共同随机种子比较；FORMAL 必须换用独立种子。CALIBRATION 结果不得并入 FORMAL，也不得用 FORMAL 结果训练搜索模型。

## FORMAL

- 每个冻结候选绑定一套查看结果前密封的 FORMAL 计划。
- FORMAL 只通过`python_bin`执行阶段 1 已认证的`.py`模拟脚本，必须绑定阶段 1 server flow 认证证据 hash；CALIBRATION 与 FORMAL 禁止执行任何服务端/JVM逻辑，`server_flow_call_count`必须为 0。
- 统计失败永久标记当前候选失败，返回 CALIBRATION 创建新候选；不得只换种子重试同一候选。
- 执行链异常修复后可按原计划重跑，不计入有效尝试。
- 默认最多 3 个不同冻结候选的有效 FORMAL 尝试。
- 完整交付前，Runtime、server、脚本、指标库、合同、豁免、作用域或计划变化时，候选和结果自动失效；server、Runtime 或脚本变化还必须退回阶段 1 重新认证。完整交付后的独立 server flow 审计不触发本规则。

最终报告严格使用`assets/templates/artifacts/04-alignment/阶段4-数值对齐报告.md`的章节顺序，由脚本确定性生成。

模板中的每一章均为展示契约，并提供固定Markdown实例：实际报告必须采用相同展示类型、字段名与字段顺序。必须展示RTP置信区间、TV桶与容差系数、Sigma、组件占比映射、评分及低分项、玩法覆盖、长尾、逐参数变化、预算与可达性上限、候选晋退、停止原因、FORMAL计划/结果/独立性、豁免阻塞、交付建议和全部hash。
