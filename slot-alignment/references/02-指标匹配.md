# 阶段 2：指标匹配

## 加载顺序

1. 固定加载`metrics/core`。
2. 按玩法画像加载 Atomic。
3. 对完整玩法加载 Composite。
4. 只有确实测量新增联合体验时加载 Interaction。

匹配条件只能使用`mechanic_id + 标准属性 + scope`。同一`metric_id + scope + semantic_group`只有一个 Owner；其他包只能引用，不能复制定义或重复计分。

## Core 硬指标

- 总 RTP。
- 完整付费入口中奖率。
- 每类适用 Feature 的自然触发概率。
- 总局倍率分布中低于 200x 的固定倍率桶。
- 总体及所有适用玩法作用域 Sigma。
- Base、Feature 和其他组件 RTP 贡献。

## 组件 RTP 贡献目标

组件 RTP 不直接使用原版绝对值。先在同一合格原版样本和同一付费入口口径下计算：

```text
component_share_i = original_component_win_i / original_total_win
component_target_i = component_share_i × authoritative_total_rtp_target
```

权威总 RTP 为区间时，对上下界分别相乘，形成组件目标区间。全部适用组件的`component_share_i`必须合计为 1，组件目标逐端点相加必须还原权威总 RTP 目标。原版总 RTP 与组件绝对 RTP只作为诊断和复算证据，不得写成目标。

使用`scripts/derive_component_rtp_targets.py`确定性生成映射结果。`metric_contract.json`必须保存`component_rtp_target_policy`；每个`core.rtp.component_contribution`实例必须保存`target_derivation.method`、`original_component_share`和原版样本证据。此规则不改变倍率桶概率分布的目标口径。

新建任务匹配 Core 后，必须读取`03B-硬指标容差系数.md`，从任务专属基础容差生成生效容差。公共指标目录只声明方法和容差来源，不直接写入某款游戏的最终容差。

固定倍率桶：

```text
0x
(0,1x)
[1x,2x)
[2x,5x)
[5x,10x)
[10x,20x)
[20x,50x)
[50x,100x)
[100x,200x)
[200x,500x)
[500x,1000x)
[1000x,2500x)
[2500x,5000x)
[5000x,10000x)
[10000x,max_win]
```

200x 及以上默认`审计`；最大观测中奖和理论最大中奖不作为硬指标。Feature Buy 回报倍数与按正常投注额计算的派奖倍数分开记录。

## 覆盖与可测

- 画像节点状态：`必需`、`可选`、`不适用`、`缺口`。
- 玩法覆盖率＝有有效 Owner 的必需画像节点数/必需画像节点总数。
- 指标可测率＝原版与候选均具备完整数据的必需指标数/已匹配必需指标总数。
- 进入 FORMAL 前：Core 完整、两项覆盖率均为 100%、无多 Owner、无未关闭必需缺口。

## 控制关系

为每个必需指标绑定`control_profile`、`coupling_cluster_id`、合法参数、预期方向、边界和证据。控制状态固定为`可控`、`只验收`、`控制关系未知`、`配置异常`。

按根因簇执行：静态控制签名 → 原版状态可分离性 → 小样本参数扰动 → 敏感性矩阵/有效秩检查。根因簇状态固定为`独立可控`、`耦合但可联合求解`、`结构冲突`、`控制证据不足`、`配置异常`。

## 完成条件

完整评价合同、Owner、目标、目标推导、作用域、数据来源、控制关系、基础容差、容差系数、生效容差、权重和版本 hash 在查看候选结果前密封。结构冲突或缺口按`02A`处理。

中文报告必须运行`render_metric_matching_report.py`生成，并严格使用阶段2模板的12章结构及逐章展示实例。字段名、字段顺序和空值表达必须与模板一致。必须分别列出玩法到指标包映射、全部指标总表、硬指标、100分评分指标、审计指标、组件RTP占比映射、容差政策、测量/评价/样本资格、控制簇可达性、缺口扩展、豁免Owner审查、合同hash和阶段3准入。
