## 执行状态

流程状态和指标结果分开记录：

| 流程状态 | 含义 | 下一步 |
|---|---|---|
| `READY` | 前置输入完整 | 进入下一阶段 |
| `PENDING_USER_INPUT` | 缺少只能由用户决定的内容 | 记录占位，可继续只读审计，不得出候选 |
| `PENDING_EVIDENCE` | 缺少画像适用性、目标来源或必需计数字段，暂时无法作出证据决策 | 继续补证；能明确判为低样本时应冻结观察项，不长期保留占位 |
| `INVALID_INPUT` | 路径、配置、Schema或hash错误 | 修复输入后重跑 |
| `RUNNING` | 阶段执行中 | 按checkpoint继续 |
| `COMPLETED` | 阶段产物已生成并通过校验 | 进入下一阶段 |
| `EXHAUSTED_NOT_PASS` | 已穷尽冻结搜索计划仍无通过候选 | 交付不通过结果，不宣称对齐完成 |

占位必须记录`field`、`status`、`reason_zh`、`owner`和`blocks`。占位不能进入冻结合同、候选参数、FORMAL结果或交付Runtime。

## 开工清单

候选出现前一次性完成下列清单。信息能从本地证据确定时直接落定；只有唯一RTP、用户认证脚本和超出默认边界的参数权限必须由用户明确确认。

| 项目 | 动作 | 产物 | 不能自动落定时 |
|---|---|---|---|
| 游戏身份 | 从项目目录、规则标题和Runtime确认游戏代码与中文名 | `game_code`、`game_name_zh` | 证据冲突时标记`PENDING_EVIDENCE` |
| Runtime候选 | 只读列举配置仓库、服务端缓存和资料目录中的完整四件套 | 候选路径、逐文件hash、bundle hash | 标记`PENDING_USER_INPUT`选择基线 |
| 原版证据 | 扫描`capture-summary/`下全部来源，并按预期指标统计有效分母、N3触发数和分布档位计数 | 根目录、来源数、完整入口数、逐指标证据表 | 缺少来源或无法确认统计口径时标记`PENDING_EVIDENCE` |
| 原始脚本 | 优先扫描`slot-docs:<game_code>/math/scripts/` | 唯一路径和SHA-256 | 多个候选且证据不能区分时标记待认证 |
| 目标RTP | 接收用户直接值或对资料候选值的明确确认 | 唯一标量和确认记录hash | 标记`PENDING_USER_INPUT`，禁止出候选 |
| 参数权限 | 读取或创建`parameter_authority.json` | 可调参数、边界、锁定项和证据 | `reel-strip`数值权重默认授权；结构变化必须待授权 |
| 玩法画像 | 按规则、Capture、脚本和Runtime建模 | `game_profile.json` | 缺口逐项标记，不整份猜测 |
| 目标证据决策 | 按最低线、建议线和分布整组规则分类 | 每个预期实例的活动/观察决定与覆盖范围 | 计数低时直接按政策落定，不等待候选结果 |
| 执行预算 | 结合固定样本政策和机器基准落定Worker/时间/磁盘 | 执行计划 | 无用户预算时由Agent按代表性基准给出有限计划并记录 |

开工信息只确认一次。后续普通候选、阶段晋级和失败重算不反复询问。

## 阶段1：输入、画像和能力

### 1.1 密封输入

1. 解析`directory_map`和`runtime_environment`，禁止测试与正式路径交叉。
2. 选定基线Runtime后，把实际四件套逐文件复制到`work/baseline/runtime/`。
3. 记录源目录ID路径、绝对解析路径、逐文件SHA-256和bundle hash。
4. 密封全部原版来源、规则、脚本和用户确认记录，后续只读。
5. 基线模拟和候选派生只读取密封封包，不再动态读取外部配置仓库或服务端缓存。

### 1.2 认证脚本与派生实现

原始认证脚本保持只读。派生观测器或快速模拟器必须证明以下语义等价：

```text
RNG调用顺序和最终状态
逐入口实际投注和总派奖
组件派奖归属
Feature进入、重触发和结束
结算与连续结算步骤
状态机、封顶和守恒
全部正式N/J/P/B原始测量
```

自然样本难以覆盖的路径使用确定性验证案例，不通过结果导向重抽制造覆盖。

### 1.3 冻结玩法画像

按[画像决策表](01-指标框架.md#画像决策表)逐项落定组件、Feature、结算、中奖组、连续结算、特色机制、盘面和Sigma作用域。每个决定必须有证据引用。

下面三类情况必须区分：

- 玩法不存在：`不适用`；
- 玩法存在但结果固定：规则审计；
- 玩法存在且结果可变：生成正式指标实例。

### 1.4 Runtime能力矩阵

从服务端实际读取逻辑和认证脚本枚举Runtime原生能力，不得把当前基线的配置数量当作能力上限。至少覆盖：

```text
ReelSet池数量
ReelSet选择作用域
reel-strip符号数量与排列
stop weights
补位profile数量
每轴补位符号权重
高度权重
特色机制权重
```

不改变盘面结构、符号域、玩法、结算、状态机和RNG顺序，只扩展原生支持的配置数量、权重或路由，属于配置能力释放，不属于玩法结构修改。例如从单ReelSet扩展为原生多ReelSet加权池，或增加Runtime原生支持的连续消除补符profile。

能力按“现有权重 → 池选择权重 → 新增原生配置项 → 各项内部strip、stop、补符或机制权重 → 合法状态路由”逐层释放。ReelSet按Runtime原生作用域抽取一次后立即生效；如作用域是整段初始盘面序列，则全部连续消除保持同一套ReelSet。补符profile可按已完成的连续中奖深度切换，并使用该profile的逐轴符号权重；禁止根据已看到的盘面、中奖或派奖重选。

每项释放能力都要记录Runtime路径、原生数量范围、参数边界、联动约束、影响指标和敏感性计划，并证明认证脚本、服务端、候选生成器、CALIBRATION、FORMAL和优化器读取同一组Runtime字段。不得使用固定数量检查、隐藏Python权重或只在调参器中生效的采样器缩窄或替代Runtime能力。

任一授权能力未完整贯通上述六层或未通过等价验证时，阶段1失败，禁止开始候选模拟。搜索成本或当前基线只用一套配置不是豁免理由。

### 阶段1门禁

| 输入 | 必须输出 | 通过条件 | 失败去向 |
|---|---|---|---|
| Runtime、原版、脚本、RTP、权限 | `input_manifest.json`、密封Runtime | 路径和hash完整 | 修复输入或保留占位 |
| 规则与证据 | `game_profile.json` | 画像无未知Owner和适用性缺口 | 补证后重编 |
| 参数授权与六层实现 | `runtime_capability_matrix.json` | `coverage_status=通过` | 扩展实现或锁定未授权能力 |
| 认证与派生脚本 | `script_equivalence.json` | RNG、状态和测量等价 | 修复派生实现 |

## 阶段2：指标合同

使用`scripts/compile_metric_contract.py`读取：

```text
game_profile.json
targets.json
contract_bindings.json
sample_execution_plan.json
runtime_capability_matrix.json
references/指标目录/index.json
五份合同政策JSON：N类通过值、统一评价、原版目标证据、样本执行和Runtime能力政策；`workspace_layout_policy.json`只负责目录落盘，不编入指标合同
```

`assets/templates/`中的JSON是填写骨架，`<...>`占位和空数组在补全前可以不满足正式Schema。`workspace_layout_policy.json`负责把任务内每个命名JSON绑定到唯一Schema；写入任务`artifacts/`或`work/`的正式记录必须立即通过该Schema。原始日志和差异文件不受JSON Schema约束，但必须由上层manifest绑定路径与SHA-256。

合同必须冻结：

- N/J/P/B全部画像命中卡、Facet、预期实例和顺序；
- 每个预期实例的Owner、作用域、样本单位、分子分母和支持；
- 目标值、来源方法、证据hash、有效样本数、事件数或档位计数；
- 候选前冻结的活动/观察决定、证据分类、原因和整体覆盖范围；
- 距离方法、自然单位、档位和聚合关系；
- C级通过值、唯一通过规则、评分政策和状态规则；
- 原版最低线、建议线、档位合并和分布整组观察证据；
- CALIBRATION和FORMAL样本计划；
- 指标库、政策、Runtime、脚本、参数权限和能力矩阵hash；
- A1、A4、A5审计定义。

N1只接受`user_confirmed_exact_rtp`。N6只接受`original_component_share_mapped_to_user_confirmed_total_rtp`。

目标侧样本不足时，不生成“假装充分”的活动目标。低于最低线的实例保留在冻结合同的观察清单；达到最低线但低于建议线的实例保持活动并标记低样本。只有缺少目标来源、样本计数或画像定义，导致无法按政策分类时，才作为合同缺口阻断候选。

### 阶段2门禁

`metric_contract.json`必须通过Schema、内部hash、外部绑定hash、卡顺序、实例唯一性、目标完整性、样本计划和能力矩阵校验。合同一旦冻结，候选结果不能改变它。

## 阶段3：基线

使用密封基线Runtime和冻结合同运行基线模拟，输出：

```text
artifacts/03-evaluation/baseline_measurements.json
artifacts/03-evaluation/alignment_result.json
artifacts/03-evaluation/stage3_gate.json
```

`baseline_measurements.json`必须通过`metric-measurements.v6` Schema，并绑定当前任务、`BASELINE`阶段和合同SHA-256。CALIBRATION与FORMAL测量使用同一Schema，只替换阶段；合同外实例直接拒绝，合同内缺失实例保留为`计算异常/U`。

每个活动实例输出目标、候选、距离、C级通过值、偏差倍数、分数、等级、状态和样本证据。观察项不要求基线测量，单独输出原版证据、观察原因和覆盖影响。通过状态只按`距离 <= C级通过值`生成；偏差倍数只用于比较、评分、排序和报告。审计单独展示，不混入正式门禁。

- `通过`：仍可继续优化，但不强制。
- `不通过`：进入CALIBRATION。
- `无法完整判定`：继续可执行流程并保留U项；若缺口来自冻结合同本身，应先修合同，不能直接FORMAL。

活动判定为`通过`时还要看覆盖范围：无观察项写`完整范围通过`，有观察项写`有限范围通过`。观察项不会把基线或FORMAL自动改成U。

`work/baseline/measurements.json`校验通过后原样晋级为`baseline_measurements.json`，两者SHA-256必须一致。阶段3只保留机器结果，不生成独立Markdown；基线信息在最终`对齐报告.md`需要时以简短说明呈现，不建立第二份报告。

`stage3_gate.json`只表示阶段3产物结构和绑定正确、允许进入阶段4，不代表基线已经通过。

## 阶段4：CALIBRATION与FORMAL

### 4.1 参数敏感性

候选前生成`sensitivity_plan.json`，逐参数记录：

```text
参数ID和Runtime位置
授权上下界或合法集合
参数类型：连续、整数、类别或结构化权重
扰动方式与固定seed
预期影响指标
实际方向和影响量
无效或耦合风险
进入哪一层搜索
```

优先使用可复现的小样本单参数扰动。权重参数按归一化前的原生整数或浮点权重扰动；reel-strip同时记录符号计数、顺序和stop weights的联动关系。

### 4.2 候选生成算法

根据参数类型选择最短、可复现的方法：

| 参数面 | 推荐方法 | 适用原因 |
|---|---|---|
| 少量近似单调参数 | 有界坐标搜索或二分式局部搜索 | 方向清楚、结果容易复盘 |
| 多个连续且互相耦合的权重 | 固定seed的CMA-ES、差分进化或等价群体搜索 | 能处理非线性和参数联动 |
| 整数计数、档位数或reel-strip | 有界邻域变异与分层搜索 | 保持合法离散结构 |
| 连续与离散混合 | 先离散拓扑、后连续权重的分层混合搜索 | 避免一次搜索空间过大 |

算法选择、seed、种群或邻域大小、最大候选数、停滞判定和升级顺序最终晋级到`artifacts/04-alignment/alignment_manifest.json`。每个`cv####/batch_manifest.json`用`search_layer_id`绑定一个冻结搜索层，并保存本批全部提案：有效候选按冻结排序元组升序放在前面，并绑定参数、测量、结果和排名；配置非法的提案放在后面，只保存拒绝原因与拟变更参数，不伪造测量或排名。每个实际使用的搜索层都必须按`SCREEN → REFINE → FINAL`完成三档，`alignment_manifest.json.calibration_batches`按`cv####`升序只做批次索引，不再建立重复的候选总表。没有用户计算预算时，Agent根据代表性吞吐基准设置有限预算并记录理由；不得使用无上限循环。

候选配置可以在模拟前因Schema、权限、权重为空或结构矛盾被拒绝；这属于配置校验。游戏随机结果生成后不得因结果不好而拒绝、回滚或重抽。

### 4.3 确定性排序

候选按以下元组从小到大排序：

```text
(
  活动N硬门禁失败数,
  活动J/P/B失败实例数,
  活动实例中的样本不足与计算异常数,
  全部可计算活动实例的最大偏差倍数,
  全部可计算活动实例的偏差倍数总和,
  candidate_id
)
```

U项可以随候选继续到更高样本档，但不能按通过计数，也不能通过缺少测量获得排序优势。`candidate_id`只作为完全平局时的稳定排序键。不得引入能补偿失败项的指标权重。

### 4.4 能力升级与终止

允许第一轮只搜索少量高敏感参数，但必须预先冻结升级层。出现以下任一情况时升级：

- 连续一层候选只改善N1，失败实例集合没有减少；
- 相较上一层的最大偏差倍数改善量未达到预设下限；
- 当前层所有候选都卡在相同结构不可达项；
- 独立复核排名明显反转，说明当前参数层不稳定。

按能力矩阵冻结的顺序逐层释放已授权的ReelSet池、选择权重、strip与stop weights、按连续消除深度切换的逐轴补符权重、高度权重和特色机制权重。升级后如果模拟器或优化器能力变化，重新做等价验证。

满足任一条件时结束CALIBRATION：

1. 前2名独立复核中至少一个候选的全部活动正式实例都满足`距离 <= C级通过值`；
2. 已穷尽冻结搜索层和候选预算；
3. 发现合同、实现或配置错误，必须修复并使旧候选失效。

第2种情况交付`EXHAUSTED_NOT_PASS`，保留最优候选和失败证据，不无限尝试。

### 4.5 固定样本阶梯

| 阶段 | 完整付费入口 | 候选范围 |
|---|---:|---|
| 初筛 | `100000` | 全部候选 |
| 复筛 | 累计`500000` | 晋级候选 |
| 决赛 | 累计`2000000` | 决赛候选 |
| 独立复核 | 另跑`2000000` | 排名前2名，独立seed |

CALIBRATION和FORMAL默认使用`chunk_seeded`。`crn_v1`只能用于隔离诊断，不得进入排序、冻结或FORMAL证据。

BASELINE、每个候选、独立复核和FORMAL都把逻辑分片写入各自`shards/shard-######.json`；分片文件同时保存聚合结果和checkpoint。

### 4.6 候选冻结

把决赛排名前2名中实际参加独立复核的候选复制到各自的`work/candidate-freeze/<candidate_id>/`，复制后不再修改参数或Runtime。先在该目录完成独立复核，再生成`freeze_manifest.json`统一绑定：

```text
完整参数和参数hash
Runtime四件套和bundle hash
指标合同hash
模拟器与观测器bundle hash
能力矩阵hash
独立复核结果
```

独立复核的分片、测量和结果固定写入`independent-recheck/`。只有复核完成且`freeze_manifest.json`通过Schema与hash校验后，才使用`--phase CANDIDATE_FREEZE`重新校验能力矩阵。`freeze_manifest.status=READY_FOR_FORMAL`只表示证据完整且可以执行FORMAL，不表示指标已经通过。冻结目录必须精确对应最后一个已完成`FINAL`批次的前2名；有效候选不足2个时按实际数量。`alignment_manifest.json.candidate_freezes`索引全部实际复核候选，并且只能有一个`selected_for_formal=true`；它表示被选去做FORMAL，同样不表示候选已经通过。

### 4.7 FORMAL

FORMAL必须使用新seed和冻结候选，重新计算全部活动合同实例。观察项只从冻结合同进入报告，不要求FORMAL生成候选测量。`formal_plan.json`在执行前冻结候选、输入hash、总入口数、基础seed和全部分片。按每个活动条件实例的整体分母暴露概率计算`ceil(2000 / probability)`，从`10000000`、`20000000`、`50000000`中选择最小覆盖档位。

不得按分布内部稀有桶提高样本。`50000000`仍不足时完成执行并标U。FORMAL失败不能换seed重刷；修复错误或修改候选后创建新的`fv####`批次，并保留旧失败批次。

FORMAL启动前使用`--phase FORMAL`再次校验同一能力矩阵hash。每个FORMAL批次都写入`alignment_manifest.json.formal_batches`，包括失败或失效批次；只能有一个已完成批次标记`promoted_to_artifact=true`。该批次必须使用唯一入选候选，其`alignment_result.json`原样晋级为`artifacts/04-alignment/formal_result.json`。

阶段4的终止状态只描述活动指标的FORMAL结论：`formal_pass`、`formal_not_pass`或`formal_undetermined`。`formal_pass`还要结合覆盖范围，在报告中落成`完整范围通过`或`有限范围通过`。即使CALIBRATION已穷尽且没有通过候选，也必须冻结证据最完整的最优有效候选并完成一次FORMAL，用正式结果证明`formal_not_pass`或`formal_undetermined`；不得留下没有来源的空`aligned_parameters.json`或`formal_result.json`。

## 阶段5：交付

交付内容至少包括：

- 五阶段权威机器JSON；
- 候选、FORMAL、Worker等价和续跑证据；
- FORMAL实际使用的Runtime四件套；
- `delivery_manifest.json`，其中`checks`只保存FORMAL来源、Runtime、版本、RTP Group和最终参数绑定检查；
- 由`input_manifest.json`、`metric_contract.json`和`formal_result.json`确定性生成的唯一`交付物/报告文档/对齐报告.md`。

版本规则固定为：

```text
game_core.json.meta.version = task_id
delivery_manifest.runtime_version = task_id
rtp_group = 1
```

不生成独立Runtime版本号。未经用户另行授权，不把交付Runtime同步到配置仓库，不提交Git，不热更新服务。

## 报告合同

最终只生成[对齐报告模板](../assets/templates/reports/对齐报告.md)对应的一份Markdown：

```text
交付物/报告文档/对齐报告.md
```

同目录保留`report_manifest.json`作为机器校验清单，但不得再生成其他Markdown、版本目录或阅读入口。
正式交付命令必须带`--task-root`；报告脚本会先校验三份输入和两个输出是否位于6.0固定路径，再更新唯一报告并生成对应`report_manifest.json`，不手工拼清单。

报告固定按以下顺序组织：

1. 对齐总览：对齐状态、总等级、综合分、覆盖范围；
2. 四大指标结果：N/J/P/B各自等级、分类分、状态和一句话结论；
3. 指标详情：在同一文件内逐项列出全部活动指标、低样本指标、观察项和不适用卡；
4. 需要关注的指标；
5. 样本与覆盖说明；
6. 最终结论。

每个指标阅读行必须包含中文名称、统计范围、一句话说明、原版目标、对齐结果、分数、状态和备注。机器实例ID、字段名、枚举值、距离算法名和完整Hash只保留在JSON，不直接展示给读者。

人类报告状态统一翻译为：

- `通过`；
- `通过（低样本）`；
- `不通过`或`不通过（低样本）`；
- `略过（无原版证据）`、`略过（原版样本不足）`或`略过（分布证据不足）`；
- `候选样本不足`；
- `计算异常`；
- `不适用`。

“略过”只表示原版证据不足，不能承担正式判定，不等于删除指标。报告必须明确：N/J/P/B活动实例共同决定通过状态，观察项只改变覆盖范围但必须完整披露；当前总等级和综合分只按N类计算，未授权跨分类权重前不得称为N/J/P/B加权总分。
