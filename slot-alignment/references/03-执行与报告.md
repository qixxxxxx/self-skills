# v5执行与报告

## 阶段1：资料与画像

密封Runtime、全部原版来源、模式、付费配置、用户确认的唯一总RTP及确认记录hash、原始脚本hash、派生脚本等价资格、玩法画像和参数权限。`reel-strip`默认作为可调数值权重，允许调整现有符号重复次数与排列；轴数、盘面几何、符号域、特殊符号限制和玩法语义保持锁定。计划确认后不得重复询问该默认权限。玩法画像必须提供结算类型、Feature、特色机制、可见盘面和符号域，供v5指标编译器生成实例。

## 阶段2：指标合同

使用`scripts/compile_metric_contract.py`读取玩法画像、`references/指标目录/index.json`和策略文件，生成`metric_contract.schema_version=slot-alignment.metric-contract.v5`。

合同必须包含：

- N/J/P/B全部适用卡、Facet、子项和作用域；
- 唯一Owner和适用性证据；
- 冻结目标及来源证据hash；N1使用用户确认总RTP，其余目标按指标合同取值；
- 距离方法、业务轴和可达支持；
- N类基础容差、系数和生效容差；
- J/P/B联合99%自对照计划和生效容差；
- 绑定评价政策中的N逐卡与J/P/B FORMAL分级阈值；
- 审计项及其派生或守恒来源；
- 指标库、政策、Runtime、脚本和参数权限hash。

不得生成权重、综合分、评分锚点或豁免实例。

## 阶段3：基线判定

使用`scripts/evaluate_alignment.py`生成：

```text
artifacts/03-evaluation/
├── alignment_result.json
└── stage3_gate.json
```

中文报告逐卡展示目标、候选、距离、容差、偏差倍数、最低通过上限、FORMAL等级、最差子项和状态。审计单独成节，不与正式门禁混合。

阶段3的`不通过`表示需要进入CALIBRATION；`无法完整判定`不停止整体流程，但必须在后续报告持续保留未判定实例。

## 阶段4：CALIBRATION与FORMAL

调参目标按以下顺序确定性比较：

1. 样本可计算的硬门禁失败数量；
2. 样本可计算的J/P/B失败子项数量；
3. 全部可计算正式实例中的最大偏差倍数；
4. 偏差倍数总和，仅用于同前三项完全相同时排序。

不得使用指标权重。结构不可达实例保留为失败，不得从目标集合移除。冻结候选后使用独立RNG分片执行FORMAL，并重新计算全部冻结实例。

FORMAL输出必须包含候选参数hash、合同hash、实际样本、逐实例偏差倍数、最低通过上限、等级、最差子项、审计、最终等级、最终状态和多Worker等价证据。FORMAL Runtime的`game_core.json.meta.version`必须严格等于当前`task_id`。

执行实现必须遵守[性能与执行预算](05-性能与执行预算.md)：完整逐局/RNG账本只用于小样本等价验证，CALIBRATION与FORMAL使用等价的流式聚合器和可校验分片checkpoint。不得把全量逐局NDJSON作为正式大样本的中间交换格式。

## 阶段5：交付

交付全部阶段机器JSON、确定性中文报告、FORMAL Runtime四件套和manifest。交付Runtime版本号固定使用`task_id`：`game_core.json.meta.version = delivery_manifest.runtime_version = task_id`；不生成独立Runtime版本号。报告必须清楚区分：

- `通过`：全部必需实例为S/A/B/C，最终等级取最差实例；
- `不通过`：无未判定项但至少一个正式实例为F级；
- `无法完整判定`：至少一个正式实例样本不足、计算异常或合同缺口；流程仍已执行和交付。

## 报告最小章节

最终交付使用[主报告模板](../assets/templates/reports/原版体验对齐报告.md)，内容按“前部结论、后部证据”组织：

1. 一页结论：最终状态、N/J/P/B分类结果、玩家体验结论、最多5个需关注项和阅读入口。
2. 任务范围与证据：Runtime、原版来源、认证脚本、参数权限及短hash。
3. 玩法画像与指标合同：只保留玩法摘要、实例数量和分类明细入口。
4. FORMAL结果：最终等级、关键数值和卡级等级，不在主报告重复全部实例。
5. 对齐过程：基线、最终CALIBRATION、FORMAL及最多10项关键参数变化。
6. FORMAL可信性：候选冻结、独立样本、种子、Worker和合同一致性。
7. 异常与审计：全部未通过、未判定项和必要审计结论。
8. 交付内容：Runtime四件套、短hash和交付检查。
9. 最终结论：状态、最差实例和机器事实源。

### 报告拆分规则

- 活动实例总数不超过40且每个分类不超过15时，可在主报告内输出简版实例明细。
- 活动实例总数超过40，或任一分类超过15时，使用[分类明细模板](../assets/templates/reports/指标分类明细.md)生成`N-数值指标.md`、`J-中奖结算.md`、`P-玩法过程.md`、`B-盘面呈现.md`中的适用文件。
- 主报告始终只展示卡级结果、关键数值、最多5个需关注项和分类文档链接，不因拆分而重复逐实例表。
- 分类明细只展开本分类；普通通过实例使用四列表格，未通过、样本不足、计算异常及本卡最差实例再使用两列详情表。
- 主报告表格最多4列；路径和完整hash不得塞入横向结果表。主报告使用短hash，完整值保留在manifest和机器JSON。
- 空章节直接删除；不得连续输出“无”“不适用”或模板占位符。

报告不得出现综合分、权重、豁免后通过或用平均结果掩盖最差子项。

## 确定性命令

全部命令使用环境解析出的`python_bin`。本机默认示例：

```bash
/Users/lq/slot_math_env/bin/python scripts/validate_metric_library.py
/Users/lq/slot_math_env/bin/python scripts/generate_metric_summary.py --check
/Users/lq/slot_math_env/bin/python scripts/calibrate_joint_tolerances.py --input <self-distance.json> --output <joint-tolerance.json>
/Users/lq/slot_math_env/bin/python scripts/compile_metric_contract.py --profile <game-profile.json> --targets <targets.json> --joint-tolerances <joint-tolerance.json> --bindings <bindings.json> --output <metric-contract.json>
/Users/lq/slot_math_env/bin/python scripts/evaluate_alignment.py --contract <metric-contract.json> --measurements <measurements.json> --phase BASELINE --output <alignment-result.json>
/Users/lq/slot_math_env/bin/python scripts/generate_stage3_gate.py --result <alignment-result.json> --output <stage3-gate.json>
/Users/lq/slot_math_env/bin/python scripts/validate_artifacts.py --contract <metric-contract.json> --result <alignment-result.json> --stage3-gate <stage3-gate.json>
/Users/lq/slot_math_env/bin/python scripts/validate_delivery.py --formal-result <formal-result.json> --runtime-dir <交付物/runtime> --manifest <delivery-manifest.json>
/Users/lq/slot_math_env/bin/python scripts/render_alignment_report.py --contract <metric-contract.json> --result <alignment-result.json> --output <report.md>
```

FORMAL把`--phase`改为`FORMAL`，并再次执行产物校验。任何命令不得从候选结果反向修改合同。
