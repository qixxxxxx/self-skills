# 7.0 轻量执行与报告

本文件规定开工准备、样本整理、指标合同、自动对齐与交付四个阶段。实现事实源只有Runtime和用户认证Python脚本。

## 一、执行状态

| 状态 | 含义 |
|---|---|
| `PENDING_USER_INPUT` | 缺少必须由用户确认的内容 |
| `INVALID_INPUT` | 路径、hash、Schema或Runtime加载失败 |
| `READY_FOR_SAMPLES` | 开工六项完整，可以整理原版样本 |
| `READY_FOR_ALIGNMENT` | 指标合同冻结，可以生成候选 |
| `READY_FOR_FORMAL` | 唯一候选和FORMAL计划已冻结 |
| `COMPLETED` | FORMAL和交付均完成 |
| `EXHAUSTED_NOT_PASS` | 授权搜索范围已穷尽，交付不通过结果 |

占位只能存在于`preflight.json`。合同、候选、FORMAL和交付不得包含未解决占位。

## 二、阶段1：开工准备

一次确认以下六项：

1. 用户认证脚本：绝对路径、SHA-256、入口函数或命令、Python环境；
2. 样本计划：原版采用范围、PROBE/SCREEN/REFINE/FINAL和FORMAL局数；
3. Runtime：唯一基线目录、四件套逐文件hash和bundle hash；
4. 调参能力：认证脚本能够读取且用户允许修改的Runtime字段；
5. 工作区：`game_code`、`mode`、`task_id`和任务根目录；
6. 游戏画像：组件、Feature、结算、连续结算、特色机制、盘面和Sigma作用域。

### 最小一致性检查

候选和FORMAL直接调用认证脚本核心。开工只检查：

- 四件套能被认证脚本加载；
- 每个授权参数路径能被认证脚本读取；
- 固定seed的小样本运行能正常完成；
- 输出能够提供合同所需的投注、派奖、状态和N/J/P/B观测数据；
- 脚本没有从原版样本查表出盘或按结果重抽。

如果额外提供快速执行层，它只能做调度和聚合，并用少量固定seed比较逐入口投注、派奖、状态、盘面摘要和最终RNG状态。脚本及快速层hash未变化时复用结果。

### 阶段产物

`artifacts/preflight.json`同时保存画像、样本计划、参数权限、Runtime和认证脚本信息。状态为`READY_FOR_SAMPLES`后进入阶段2。

## 三、阶段2：样本整理

只读扫描用户确认采用的全部原版样本，生成一份`artifacts/source_summary.json`。

至少汇总：

```text
完整付费入口
投注与总派奖
各组件派奖
Feature进入与完整周期
正奖励结算步骤
连续结算深度
特色机制机会和结果
各稳定盘面作用域
每个正式分布桶的计数
```

每个目标保存目标值、样本数、事件数或桶计数、证据引用和证据状态。默认不保存全量逐入口事件，也不为每个实例建立独立证据文件。排错需要的事件样本必须有固定上限，且不能参与候选出盘。

原版来源和整理逻辑hash不变时允许复用`source_summary.json`。

## 四、阶段3：指标与评分合同

`compile_metric_contract.py`读取`preflight.json`和`source_summary.json`，按指标目录和政策生成`artifacts/metric_contract.json`。

合同冻结：

- N/J/P/B全部画像命中实例及稳定顺序；
- 活动、低样本活动、观察和不适用决定；
- Owner、作用域、样本单位、分子分母和支持；
- 目标、来源、证据计数和证据分类；
- 距离、C级通过值、偏差倍数、评分和汇总；
- 候选样本阶梯、FORMAL样本数和独立seed要求；
- Runtime bundle、认证脚本、原版样本、画像和参数权限hash。

合同冻结后，业务内容变化会使候选失效；Worker数、micro-batch大小和checkpoint位置不属于业务合同，只要不改变seed映射和结果即可调整。

合同通过Schema、实例完整性、目标证据、政策绑定和内部hash检查后，状态为`READY_FOR_ALIGNMENT`。

## 五、阶段4：自动对齐、FORMAL与交付

### 4.1 基线

基线直接作为`candidate_id=baseline`写入候选账本。它使用冻结Runtime、认证脚本和合同：

- 基线通过：允许直接选为FORMAL候选；
- 基线不通过：进入参数敏感性和候选搜索；
- 基线存在U项：可以继续诊断和候选，但不能宣称通过。

不生成独立阶段门禁文件。

### 4.2 候选

优化器只能生成授权Runtime参数。模拟、RNG、盘面、Feature和结算始终由认证脚本完成。

普通候选只写入`work/candidate_ledger.jsonl`：

```text
candidate_id
父候选
参数差量与参数hash
基线Runtime bundle hash
候选Runtime bundle hash
认证脚本hash
指标合同hash
seed计划
累计样本数
N/J/P/B评价摘要
确定性排名元组
状态
```

交付校验会逐行检查候选账本：每条候选都必须绑定用户认证脚本和当前指标合同，唯一入选记录的参数hash与Runtime bundle hash必须和`alignment_manifest.json`一致。

候选默认按`PROBE → SCREEN → REFINE → FINAL`增加样本。升级和提前停止条件必须在`preflight.json`中确认，不能根据想要的结果临时修改。

只有唯一入选候选才写入`work/selected/runtime/`完整四件套和`artifacts/alignment_manifest.json`。不再固定复核前2名，FORMAL本身承担独立验证。

### 4.3 FORMAL

FORMAL必须：

1. 使用唯一入选候选的原样Runtime；
2. 使用与候选相同的认证脚本SHA-256；
3. 使用预先冻结的新独立seed；
4. 重新计算全部活动实例；
5. 不读取候选聚合结果作为FORMAL测量；
6. 失败后不得换seed重刷。

FORMAL测量和评价合并为`artifacts/formal_result.json`。若最大样本仍不足，受影响实例标为`样本不足/U`。

### 4.4 交付

交付：

- `artifacts/preflight.json`
- `artifacts/source_summary.json`
- `artifacts/metric_contract.json`
- `artifacts/alignment_manifest.json`
- `artifacts/formal_result.json`
- `artifacts/delivery_manifest.json`
- `交付物/runtime/`四件套
- `交付物/报告文档/对齐报告.md`

`delivery_manifest.json`只校验任务、认证脚本、指标合同、FORMAL、Runtime逐文件hash、RTP Group和版本。报告由preflight、合同和FORMAL结果确定性生成。

如果搜索穷尽仍无通过候选，冻结最优有效候选并执行一次FORMAL，交付失败指标、已尝试参数面和下一步建议，状态为`EXHAUSTED_NOT_PASS`。

## 六、报告

报告只保留一份Markdown，顺序固定为：

1. 对齐状态、等级、分数和覆盖范围；
2. N/J/P/B分类结论；
3. 全部活动指标；
4. 低样本和观察项；
5. 不通过或无法判定项；
6. 样本、认证脚本和Runtime说明；
7. 最终结论。

报告使用中文名称、自然单位和口语化说明，不直接堆放JSON字段名和完整hash。
