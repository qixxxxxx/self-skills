# v5执行与报告

## 阶段1：资料与画像

密封Runtime、全部原版来源、模式、付费配置、用户确认的唯一总RTP及确认记录hash、原始脚本hash、派生脚本等价资格、玩法画像和参数权限。`reel-strip`默认作为可调数值权重，允许调整现有符号重复次数与排列；轴数、盘面几何、符号域、特殊符号限制和玩法语义保持锁定。计划确认后不得重复询问该默认权限。玩法画像必须提供结算类型、Feature、特色机制、组件、界面展示投注基准、互斥中奖组、每种结算模型唯一主要结构轴、J2/J3维度可变性、连续结算作用域、`initial/cascade_visible`正式盘面、互斥视觉符号组、关键计数符号和关键空间符号，供v5.2指标编译器生成实例。terminal原始观测保留为A5审计，不与initial重复计分。

候选出现前必须从认证脚本和服务端Runtime读取实现中枚举原生调参能力，生成`artifacts/01-input-profile/runtime_capability_matrix.json`。矩阵逐项记录认证脚本、服务端、候选生成器、CALIBRATION模拟器、FORMAL模拟器和优化器的支持范围，至少覆盖ReelSet路由列表、选择作用域、reel strips、stop weights、补位档、每轴补位符号权重、高度权重及特色机制权重。基线当前只有两套ReelSet或一个编号补位档，不代表原生上限就是2或1。

每项已授权能力必须同时满足：候选生成器可表达、CALIBRATION和FORMAL可执行、优化器已暴露参数且存在确定性敏感性或升级计划、派生实现与认证脚本等价。任一层缩窄数量或档位时，阶段1不通过，禁止开始候选模拟。搜索空间较大、当前实现方便或预计吞吐下降不能作为豁免理由。

## 阶段2：指标合同

使用`scripts/compile_metric_contract.py`读取玩法画像、`references/指标目录/index.json`和策略文件，生成`metric_contract.schema_version=slot-alignment.metric-contract.v5`。

合同必须包含：

- N/J/P/B全部适用卡、Facet、子项和作用域；
- 唯一Owner和适用性证据；
- 冻结目标及来源证据hash；N1使用用户确认总RTP，其余目标按指标合同取值；
- 距离方法、业务轴和可达支持；
- N类基础容差、系数和生效容差；
- J/P/B联合99%自对照计划和生效容差；
- 候选与FORMAL样本执行计划、样本策略hash和计划hash；
- 绑定评价政策中的N逐卡、J、P与B FORMAL分级阈值；
- 审计项及其派生或守恒来源；
- 指标库、政策、Runtime、脚本和参数权限hash。
- Runtime能力矩阵hash及能力覆盖政策hash；矩阵状态必须为“通过”。

不得生成权重、综合分、评分锚点或豁免实例。

## 阶段3：基线判定

使用`scripts/evaluate_alignment.py`生成：

```text
artifacts/03-evaluation/
├── alignment_result.json
└── stage3_gate.json
```

中文报告逐卡展示目标、候选、距离、容差、偏差倍数、最低通过上限、FORMAL等级、最差子项和状态。审计单独成节，不与正式门禁混合。

阶段3的`不通过`表示需要进入CALIBRATION；`无法完整判定`不停止整体流程，但必须在后续报告持续保留未判定实例。

## 阶段4：CALIBRATION与FORMAL

调参目标按以下顺序确定性比较：

1. 样本可计算的硬门禁失败数量；
2. 样本可计算的J/P/B失败子项数量；
3. 全部可计算正式实例中的最大偏差倍数；
4. 偏差倍数总和，仅用于同前三项完全相同时排序。

在上述确定性排序下，CALIBRATION默认持续优化到全部J/P/B实例达到B级及以上，即`J<=4.0`、`P<=5.0`、`B<=6.0`。最终候选存在C级时仍可进入FORMAL，但报告必须标记“最低通过”，不得把C级描述为基本一致或稳定一致。

优化器可以从低维参数开始，但能力矩阵必须预先声明升级顺序。连续候选只改善RTP而结构失败数、最差实例或最大偏差没有实质改善时，必须逐层开放已授权原生能力，例如分离Base/Free与各ReelSet、分离每轴stop weights、分离`refill_1/final`、增加按Tumble深度的编号补位档、增加职责不同的ReelSet，以及启用特色机制权重。不得因候选生成器或快速模拟器暂未实现而把已授权能力当作不可用。

候选固定使用以下累计样本阶梯，不再逐任务临时设计局数：

1. 全候选初筛`100000`局；
2. 晋级候选累计到`500000`局；
3. 决赛候选累计到`2000000`局；
4. 排名前2名各自另跑`2000000`局独立复核，复核样本不得与前三档复用。

CALIBRATION与FORMAL默认使用`chunk_seeded`。`crn_v1`只允许作为隔离的离线诊断，不得进入候选排序、候选冻结或FORMAL证据。不得使用指标权重。结构不可达实例保留为失败，不得从目标集合移除。

冻结候选后使用独立seed执行FORMAL，并重新计算全部冻结实例。FORMAL只允许`10000000`、`20000000`、`50000000`三档：对每个活动条件指标实例记录“完整付费入口进入该实例整体有效分母”的原版暴露概率，按`ceil(2000 / 暴露概率)`计算需求，选择能让全部条件实例达到至少`2000`个预计有效样本的最小档位。不得按分布内部某个稀有状态或偶发桶反推局数。若`50000000`仍不足，仍自动执行该档，不暂停询问；完成后把对应实例标为`样本不足/U`，最终状态按评价合同成为`无法完整判定`。

FORMAL失败不得更换seed反复重跑直到通过。只有合同、实现或配置错误被修复，或候选参数发生变化时，才能创建新的独立FORMAL批次，并保留旧失败证据。

候选冻结和FORMAL启动前分别使用`--phase CANDIDATE_FREEZE`、`--phase FORMAL`重新执行Runtime能力覆盖校验，且矩阵hash必须与合同绑定一致。快速模拟器、候选生成器或Runtime拓扑发生能力扩展时，旧脚本等价证据和旧候选结果失效，重新完成等价验证与候选阶梯；指标目标和容差未变化时不从候选结果反向修改它们。

FORMAL输出必须包含候选参数hash、合同hash、实际样本、逐实例偏差倍数、最低通过上限、等级、最差子项、审计、最终等级、最终状态和多Worker等价证据。FORMAL Runtime的`game_core.json.meta.version`必须严格等于当前`task_id`。

执行实现必须遵守[性能与执行预算](05-性能与执行预算.md)：完整逐局/RNG账本只用于小样本等价验证，CALIBRATION与FORMAL使用等价的流式聚合器和可校验分片checkpoint。不得把全量逐局NDJSON作为正式大样本的中间交换格式。执行前吞吐基准只用于记录和优化，不是阻塞门禁。

## 阶段5：交付

交付全部阶段机器JSON、确定性中文报告、FORMAL Runtime四件套和manifest。交付Runtime版本号固定使用`task_id`：`game_core.json.meta.version = delivery_manifest.runtime_version = task_id`；不生成独立Runtime版本号。报告必须清楚区分：

- `通过`：全部必需实例为S/A/B/C，最终等级取最差实例；
- `不通过`：无未判定项但至少一个正式实例为F级；
- `无法完整判定`：至少一个正式实例样本不足、计算异常或合同缺口；流程仍已执行和交付。

## 报告最小章节

最终交付使用[主报告模板](../assets/templates/reports/原版体验对齐报告.md)，内容按“前部结论、后部证据”组织：

1. 一页结论：最终状态、N/J/P/B分类结果、玩家体验结论、最多5个需关注项和阅读入口。
2. 任务范围与证据：Runtime、原版来源、认证脚本、参数权限及短hash。
3. 玩法画像与指标合同：只保留玩法摘要、实例数量和分类明细入口。
4. FORMAL结果：最终等级、关键数值和卡级等级，不在主报告重复全部实例。
5. 对齐过程：基线、最终CALIBRATION、FORMAL及最多10项关键参数变化。
6. FORMAL可信性：候选冻结、独立样本、种子、Worker和合同一致性。
7. 异常与审计：全部未通过、未判定项和必要审计结论。
8. 交付内容：Runtime四件套、短hash和交付检查。
9. 最终结论：状态、最差实例和机器事实源。

### 报告拆分规则

- 活动实例总数不超过40且每个分类不超过15时，可在主报告内输出简版实例明细。
- 活动实例总数超过40，或任一分类超过15时，使用[分类明细模板](../assets/templates/reports/指标分类明细.md)生成`N-数值指标.md`、`J-中奖结算.md`、`P-玩法过程.md`、`B-盘面呈现.md`中的适用文件。
- 主报告始终只展示卡级结果、关键数值、最多5个需关注项和分类文档链接，不因拆分而重复逐实例表。
- 分类明细只展开本分类；普通通过实例使用四列表格，未通过、样本不足、计算异常及本卡最差实例再使用两列详情表。
- 主报告表格最多4列；路径和完整hash不得塞入横向结果表。主报告使用短hash，完整值保留在manifest和机器JSON。
- 空章节直接删除；不得连续输出“无”“不适用”或模板占位符。

报告不得出现综合分、权重、豁免后通过或用平均结果掩盖最差子项。
