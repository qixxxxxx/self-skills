# 跨阶段一致性

每个阶段输出都绑定`task_id`、`game_code`、`mode`、`rtp_group`、目标 RTP、Schema 版本、生成器版本和输入 hash。

最小失效规则：

| 变化 | 最小退回 |
|---|---|
| 规则、协议、server、脚本、Runtime、作用域、参数权限 | 阶段 1 |
| 玩法画像、语义库、指标库、Owner、控制关系、豁免 | 阶段 2 |
| 目标、组件RTP贡献占比或映射政策、基础容差、容差系数、容差政策、评价合同、权重、评分脚本 | 阶段 2；评分变化继续退回阶段 3 |
| 候选参数、样本计划、种子、预算、可达性上限状态、FORMAL 计划 | 阶段 4 |
| 仅报告或清单生成器且机器事实未变 | 重生成并复验阶段 4/5 |

检查上一阶段输出可直接成为下一阶段输入；禁止同名不同义、单位变化、范围变化、重复 Owner、循环依赖和 Markdown 与 JSON 状态不一致。

阶段转换是强制机器门禁，不是展示步骤。阶段3到阶段4必须同时满足：固定scorecard存在、阶段3中文报告为当前机器结果的确定性输出、基线测量源及合同hash有效、评分可判定、`stage3_gate.json`通过。缺少任一项时，即使`work/`中已有基线或候选scorecard，也不得创建新候选或继续CALIBRATION。

v2.5起，阶段1至5中文报告都绑定统一报告展示契约：模板逐章规定展示方式、必需字段及顺序、空值规则和Markdown实例；模板和实报的章节顺序必须一致，各章节必须有内容，字段不得缺失，表头不得改名或调序，实报不得残留占位符，并且必须与当前机器JSON确定性重渲染结果逐字一致。阶段3转换门禁复核阶段1至3；阶段4预交付校验复核阶段1至4；最终交付校验复核全部五阶段。

阶段3到阶段4门禁属于流程完整性修复，不是评价标准变更。已有任务只要尚未完成并需要重新进入阶段4，也必须先补齐真实阶段3产物并通过门禁；不得根据后续候选结果倒推或改写阶段3基线。已完成历史交付不回溯重写。

已有任务不得因默认容差政策升级而自动失效；只有任务主动采用新政策时才创建新合同版本并按上表退回。

组件 RTP 占比映射和预算可达性上限作为新任务默认政策；已有已密封任务不自动回溯，只有主动采用时才创建新合同版本并按上表退回。
