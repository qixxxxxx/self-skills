# 阶段 2A：可达性、指标扩展与豁免

## 提前避免无效调参

完整搜索前必须先做配置结构检查。重点识别：多个指标共享同一权重而目标方向冲突、参数未实际生效、合法空间过窄、归一化抵消、状态不可分离、配置层级被覆盖、Runtime 与 server 读取源不一致。

只有根因簇为`独立可控`或`耦合但可联合求解`才准入完整调参。`配置异常`先修复配置；`控制证据不足`先补证；不得直接豁免。

## 结构不可达与预算上限

只有在授权参数空间已完成静态检查、方向扰动、主要控制簇的独立与联合验证，并有稳定支配、冲突曲线、边界扫描或连续插值证据时，才能密封`结构不可达`。证据必须列出已覆盖空间、未覆盖空间、候选数量、样本资格、冲突指标和最小扩权方向。

`结构不可达`一经密封，立即把`budget_expansion_allowed`设为`false`。此后禁止仅增加候选数、样本量、随机种子、运行时间或重复同类搜索。证据通过`attainability-evidence.schema.json`后，按用户预授权政策自动豁免`affected_metric_instances`中的精确实例，重算有序指标清单、评分组权重和样本能力，并退回阶段3重生成评分与门禁。未列入证据的指标不得连带豁免。

## 指标库扩展

- 缺少玩法语义：开工前提案同时列出玩法语义目录、指标包、Owner、测量合同和报告展示的扩展范围，由用户决定后再实施。
- 已有语义但缺指标：在正式开工前预检中一次汇总全部缺口，生成 JSON 与中文提案。
- 用户决定前只生成草案，不修改正式目录；批准后先完成扩库和观测/输出脚本适配，再自动完成原始认证脚本到派生脚本的等价验证与失败修复循环后正式开工，不追加用户认证。
- 批准后从`assets/catalog-templates/`创建包，更新索引、版本和 hash，运行 Schema、ID、Owner、引用及正反例校验，然后自动重新匹配。
- 用户拒绝必需缺口时保持阻塞；拒绝可选缺口时带警告继续且不计入覆盖率和评分。所有决定都在开工前完成，正式执行中不追加提问。

## 指标豁免

只允许两类自动豁免：纯样本计数不足，或合法授权参数空间已由密封证据证明结构不可达。定义缺失、目标缺失、测量输出缺失、实现错误、配置异常、预算耗尽和未知玩法不可自动豁免。

用户已预授权`automatic-metric-waiver-v1`对上述两类原因自动批准；其他原因仍只能由用户在开工前或最终报告窗口单次决定。豁免绑定游戏、mode、RTP group、Runtime、脚本、指标库、合同和参数授权hash；任一变化后自动失效。

样本不足必须已有合法`sample_capability_input`与可复算`sample_capability`，且阻塞只由`actual < required`产生。缺少逐指标计数、条件组键不一致、统计输出异常或支持集无法解析属于实现/合同错误，不得生成`AUTO_WAIVED_INSUFFICIENT_DATA`。

批准后：

- 指标仍展示目标、结果、差距和审计证据。
- 非硬指标从同父级评分分子和分母移除，剩余原权重按比例重归一化。
- 硬指标显示`硬指标已豁免`，不得显示`通过`。
- 存在任一必需豁免时，最终最多为`豁免后通过`。
- 报告必须显示原因码、精确实例ID、授权来源、政策hash、目标hash、所需/实际/缺口或不可达证明；不得只显示“已批准”。
