# 阶段 2A：可达性、指标扩展与豁免

## 提前避免无效调参

完整搜索前必须先做配置结构检查。重点识别：多个指标共享同一权重而目标方向冲突、参数未实际生效、合法空间过窄、归一化抵消、状态不可分离、配置层级被覆盖、Runtime 与 server 读取源不一致。

只有根因簇为`独立可控`或`耦合但可联合求解`才准入完整调参。`配置异常`先修复配置；`控制证据不足`先补证；不得直接豁免。

## 指标库扩展

- 缺少玩法语义：退回阶段 1 扩展语义库。
- 已有语义但缺指标：暂停阶段 2，一次汇总全部缺口，生成 JSON 与中文提案。
- 用户批准前只生成草案，不修改正式目录。
- 批准后从`assets/catalog-templates/`创建包，更新索引、版本和 hash，运行 Schema、ID、Owner、引用及正反例校验，然后自动重新匹配。
- 用户拒绝必需缺口时保持阻塞；拒绝可选缺口时带警告继续且不计入覆盖率和评分。

## 指标豁免

只有`结构冲突`、合法参数空间已证明不可达、或没有授权控制手段时可申请。数据缺失、定义缺失、目标缺失、实现错误和配置异常不可豁免。

AI 生成原因、证据、受影响范围和建议；只有用户可批准、部分批准、拒绝或撤销。豁免绑定游戏、mode、RTP group、Runtime、server、脚本、指标库、合同和参数授权 hash；任一变化后自动失效。

批准后：

- 指标仍展示目标、结果、差距和审计证据。
- 非硬指标从同父级评分分子和分母移除，剩余原权重按比例重归一化。
- 硬指标显示`硬指标已豁免`，不得显示`通过`。
- 存在任一必需豁免时，最终最多为`豁免后通过`。
